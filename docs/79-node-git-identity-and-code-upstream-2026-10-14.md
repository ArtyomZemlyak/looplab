# 79. Git-идентичность попыток, фактический конфиг и доставка кода в репозиторий задачи (2026-10-14)

*EN summary: every evaluated attempt becomes a commit of a run-owned private git repository (not a
worktree of the operator's repo), its effective hyperparameters are recorded and checked against the
declared ones, external agents get worktrees/patch intake over that repository, and the run's fixes
export into the task repository as a new branch. Revisits doc 37 with a measurement.*

**Статус (2026-10-14): реализовано, тесты `tests/test_code_identity.py`; живой GPU-прогон с
включённой записью ещё не проводился (см. §9).** Операторский путь — [guide/code-identity.md](guide/code-identity.md).

**Статус (2026-10-16): версия 2 — первая база получила родителя, коммит HEAD оператора (история в
worktree, `git diff HEAD base` = некоммитнутые правки), merge-родители честные (§10). Репозиторий
оператора по-прежнему только читается.**

## 1. Проблема

Запрос оператора: «лучшие наработки и фиксы со всего рана должны стекать в репу; git worktree».
Ночь 2026-10-13/14 показала, почему этого не происходило:

- Узлы работают на материализованных копиях (doc 37), а дифф узла — это `node.files`, не коммит.
  Ни одна попытка не имела git-идентичности, по которой её можно отревьюить или вмержить.
- Внешний агент (Codex) правил код не через узлы, а в некоммитнутых копиях источника
  (`/dev/shm/two-stage-*/repo`, не git). Фикс LR-warmup лежал коммитом `a92ba534a` в отдельном
  worktree, two-stage guard и фикс `max_steps` — только в копиях. В ветку задачи не попало ничего.
- Полоса upstream (doc 72 §18, doc 73 §2) двигает базу внутри прогона, но выхода в репозиторий
  задачи у неё не было (doc 72 §19, O14), а для внешних прогонов без блока `upstream` она не работает.
- Doc 77 §1–§2: неизвестно, какой код фактически исполнялся и с какими lr/batch/seed/steps — у узлов
  было `applied_params={}`, реальные числа жили только в логе стадии и во внешнем `protocol.json`.

## 2. Решение и замер против doc 37

Doc 37 отклонил `git worktree` **исходного репозитория** для рабочих каталогов узлов по двум
дисквалифицирующим причинам: (§5c) рабочее дерево подключено к объектной базе оператора, и
`git add -A` в узле затягивает туда гигабайты чекпойнтов; (§5d) worktree засевает HEAD, а не
рабочее дерево оператора — на v1 10 из 17 файлов были бы не те. Обе причины остаются в силе,
поэтому решение doc 37 для **рабочих каталогов узлов не меняется**: узел исполняется на копии.

Новое: **git-идентичность даётся не рабочему каталогу, а попытке** — дешёвым эквивалентом
worktree. У каждого прогона свой приватный bare-репозиторий `RUN_DIR/code/repo.git`:

- **базовый коммит** на каждый архив засева (`base_snapshots/<digest>`) — дерево ровно из
  архива, т.е. рабочее дерево оператора с некоммитнутыми правками и неотслеживаемым скорером
  (закрывает doc 37 §5d);
- **коммит попытки** на каждую материализацию жизненного цикла узла — база + оверлей, прочитанный
  с диска после материализации; родитель — база, на которой узел засеян. `git show` коммита =
  ревью изменения узла. Ремонт внутри цикла даёт второй коммит поверх первого.
- Репозиторий приватный: объектная база оператора недоступна по построению (закрывает doc 37 §5c).
  Worktree выдаются только внешним агентам и только из этого репозитория (§4).

Замер (`benchmarks/node_git_identity_cost.py` на клоне MiniOneRec `work-train`, 741 файл,
13.8 МБ; tmpfs, 7 повторов, медиана):

| операция | время | примечание |
|---|---|---|
| засев копией (как сейчас) | 0.064 с | на каждый узел, не меняется |
| `git worktree add`+`remove` исходного репо (арм doc 37) | 0.096 с | отклонён по §5c/§5d |
| базовый коммит из архива (fast-import) | 0.60 с | один раз на базу |
| коммит попытки, 1 файл (env-оверлей) | 0.0075 с | чистый fast-import |
| полная запись попытки (`record_attempt`, на архиве живого g-v3) | 0.026 с | lineage, ref, diffstat |
| коммит попытки, 20 файлов | 0.028 с | |
| worktree агента из приватного репо | 0.097 с | только по запросу (§4) |
| размер репо: база / +50 попыток | 9.56 МБ / 10.38 МБ | ~16 КБ на попытку |

На фоне оценки узла (часы на GPU) запись попытки — 26 мс; одноразовая база — 0.6 с. Дисковая цена —
сжатая копия базы (~70 % архива засева) плюс килобайты на попытку.

## 3. Запись в журнале и репозитории

- `code_snapshot` (DIAGNOSTIC, fold его не читает, fence-нейтрален) — `{node_id, generation,
  seed_event_seq, commit, base{digest,commit}, changed[], stats, source, status}`; пишется
  `engine/code_identity.py::record_materialized` из `WorkspaceSeeder.materialize` для собственного
  каталога узла (канарейка и confirm — тот же код, не новая попытка) и
  `record_after_terminal` после терминала, если оверлей изменился в ходе оценки (ремонт).
- Ссылки: `refs/heads/base` (активная база), `refs/looplab/bases/<digest>`, `refs/heads/nodes/n<id>`,
  `refs/looplab/attempts/n<id>/g<gen>/s<seed_seq>[-repair]`, `refs/heads/champion`, `agent/<name>`.
  Ссылка ремонта — соседняя, не вложенная: git не может держать `…/s5` и `…/s5/repair` сразу.
- Линия баз (`base_lineage`): первая база — корень (с версии 2 — дочерняя к коммиту оператора, §10);
  база из `base_advanced` — дочерняя к
  заменённой (с предложением, узлом-источником, флагом и gate-доказательством в трейлерах);
  новый дайджест без продвижения — `source_changed` (оператор поменял источник посреди прогона).
  Кандидатные засевы полосы (`workspace_seeded` без узла) базой не считаются, пока нет продвижения.
- Детерминизм: фиксированная идентичность и время события → те же входы дают те же id коммитов.
  Старые прогоны: `sync_run` строит те же коммиты из журнала (`source: "log"`), событий не пишет.
  Попытка — только засев собственного каталога узла (`code_identity.py::lifecycle_seeds`):
  `workspace_seeded.workdir` отличает его от канарейки, confirm и noise floor; в старом журнале без
  этого поля берётся первый засев жизненного цикла.
- Сбой git или архива — запись `status: unavailable` с причиной, никогда не отказ оценки.

## 4. Внешние агенты

Три способа подать код, все сводятся к обычному оверлею `inject_node`:

1. `files`/`deleted` — как раньше.
2. Worktree от LoopLab: `looplab code-worktree RUN name` или `POST /api/runs/{id}/code/worktrees` →
   `RUN_DIR/code/worktrees/<name>` на ветке `agent/<name>` от активной базы (или `node:<id>`). Агент
   правит, запускает, коммитит; `inject_node` с `code_from: {"worktree": name}` превращает
   «база засева → текущее состояние» (коммиты, некоммитнутые правки, новые файлы) в оверлей. От
   `node:<id>` это изменение самого узла плюс правки агента: оверлей материализуется поверх базы,
   а не поверх узла (`code_worktree.py::_seed_base_of`). Путь вне поверхности, который агент оставил
   как в стартовом коммите (актив задачи), не отказ, а наследство (`inherited_outside_surface`).
3. Патч: `code_from: {"patch": "<unified diff>", "start": "base"}`.

Оверлей проверяется той же `SurfacePolicy`, что и полоса upstream (поверхность правки и защищённые
файлы), и её же лимитами (128 путей, 2 МиБ текста). `POST /code/overlay` — предпросмотр без
отправки; ответ говорит `stale_base`, если worktree начат не от текущей базы. Источники не в git
получают git-снимок автоматически: базовый коммит строится из архива засева, а не из git источника.

## 5. Экспорт в репозиторий задачи

`looplab code-export RUN --repo <task-repo> [--branch] [--onto] [--prefix] [--node champion|N|none]
[--patches DIR] [--dry-run]` создаёт **новую ветку** (по умолчанию `looplab/<run_id>`):

1. `base` — код, с которого стартовал прогон. Если коммит источника, записанный в `run_started`,
   есть в целевом репо, это ДЕЛЬТА «этот коммит → засев» (только некоммитнутые правки), наложенная
   на `--onto` по путям с трёхсторонним слиянием — поэтому второй прогон, экспортированный поверх
   ветки первого, не откатывает его изменения. Иначе (источник не git) цель приводится к байтам
   засева по каждому его пути. `--onto` по умолчанию — тот же записанный коммит, иначе HEAD.
   Удалений шаг не делает: путь, которого нет в снимке, считается (`not_in_snapshot`).
2. `upstream` — каждое продвижение базы полосой, с доказательством гейта в трейлерах.
3. узел — изменение чемпиона (или указанного узла) с метрикой. Только коммит ЭТОГО жизненного
   цикла (записанный или построенный `sync_run`); без него шаг пропускается — ветка `champion`
   может указывать на прежнего чемпиона и запасным вариантом не служит.

Записанный коммит источника — только у `editable:` (корневого, иначе общий для всех именованных),
никогда у `data:*`/`ref:*`. Префикс по умолчанию читается через адаптер задачи (`repo`,
`editable_path`, `editables`, `~`): корневой редактируемый определяет его; только именованные —
общий каталог P с `P/<имя>` у каждого, иначе отказ `export_prefix_ambiguous` до `--prefix`.

Механика: plumbing во временном индексе (`hash-object`, `update-index`, `write-tree`, `commit-tree`),
затем `update-ref` новой ветки с нулевым старым значением. HEAD, индекс, рабочее дерево, другие
ветки, remotes и конфиг оператора не трогаются; push не выполняется никогда. Путь применяется,
если в цели старые байты прогона (или уже новые); иначе — текстовое трёхстороннее слияние
(`git merge-file`); конфликт останавливает экспорт до этого коммита и называет пути. Содержимое
сравнивается по blob, режим разрешается отдельно (`_merged_mode`): `chmod` переносится и с
изменением текста, и без него; режим, который цель сдвинула иначе, — конфликт (`mode_conflicts`), а
не выбор стороны; удаление требует в цели то же содержимое (её `chmod` — не содержимое). Базовый шаг
учитывает режим рабочего дерева засева, только если ни цель, ни ИСТОЧНИК не говорят
`core.fileMode=false` (§11).
`--patches` дополнительно пишет серию `format-patch` для merge request.

## 6. Фактический конфиг (doc 77 §2)

`core/effective_config.py::capture` на чтении метрики собирает значения в канонических ключах
(`lr`, `batch_size`, `micro_batch_size`, `grad_accum`, `world_size`, `seed`, `max_steps`, `epochs`,
`warmup_steps`, `warmup_ratio`, `scheduler`, `weight_decay`) из трёх именованных источников:
окружение, переданное командой оценки (без секретов), `KEY=VALUE` env-файлов оверлея и дампы конфига
в логах стадий (`LR: 2e-4`, `Batch: 1024 (micro=128)`, `SFT_LEARNING_RATE=…`). Объявленные
`Idea.params` сверяются: `checked` — значение совпало, `mismatches` — наблюдались другие, `unknown` —
ничего не наблюдалось (не ноль и не согласие); префикс `stage2_` ограничивает сверку логом стадии.
Два разных значения в одной стадии — `conflicts`. Событие `effective_config` (DIAGNOSTIC) пишется
после терминала. На логах живого g-v3: `lr=2e-4, batch=1024, world=8, epochs=1` по обеим стадиям,
`stage2_lr` проверен, `stage2_warmup`/`steps`/`seed` — `unknown` (guard печатает их без разделителя).

## 7. Вид оператора: что ждёт upstream

`GET /api/runs/{id}/code` и `looplab code-status RUN` — одна проекция (`code_status`, только чтение):
базы с причиной и доказательством, попытки (коммит, изменённые пути, метрика, статус, чемпион,
фактический конфиг и расхождения), `upstream.proposals`/`in_flight` с узлом-источником, его метрикой
и последним вердиктом гейта (проверки, дельта, число исполнений), `nominations` (непродвинутые
capability-ханки измеренных узлов), а для прогонов без полосы — `unlaned_changes`: измеренные
попытки, менявшие код, а не только рецепт. `GET /code/diff?commit=` — ограниченный дифф коммита.
Поля простые (строки/числа/списки) — UI-ветка может показать их в Inspector (SourceSnapshotPanel /
RuntimeSnapshotPanel из doc 77).

Полоса upstream (auto/propose/off) не изменена: она по-прежнему продвигает базу только через
измеренный гейт; новые базы автоматически становятся коммитами ветки `base`, а `code-export`
переносит их в репозиторий задачи.

## 10. 2026-10-16: base parented on the operator's HEAD; honest merge parents

Запрос: worktree агента должен быть настоящим worktree репозитория задачи с его историей, а узлы —
сливаемыми средствами git. Решение doc 37 для рабочих каталогов узлов не меняется (узел исполняется
на копии), и репозиторий оператора по-прежнему **только читается**: ни ref, ни объект, ни конфиг, ни
индекс туда не пишутся (тест: `.git` оператора побайтно тот же, `rev-list --count --all` прежний).

**Версия 2 (`code_identity.py::SNAPSHOT_VERSION`).**

- **Первая база** — дерево по-прежнему ровно архив засева (материализация читает архив, а не дерево
  коммита), но родитель — коммит, на котором стоял корневой редактируемый источник в момент старта
  (`run_started.workspace["editable:."]`, то же значение, что читает `_recorded_source_commit`
  экспорта). В worktree `git log`/`blame` показывают историю оператора, а `git diff <HEAD> base` —
  ровно некоммитнутые правки и неотслеживаемый скорер (doc 37 §5d остаётся закрытым).
- **Замер, изменивший предложенный дизайн** (git 2.43): коммит, чей родитель отсутствует в
  репозитории, НЕ становится пригодным от строки в `$GIT_DIR/shallow` — `log`, `rev-list`, `fsck` и
  `bundle create` падают с «Could not read <parent>». Нужны объекты родителя (коммит и дерево) со
  срезом shallow на нём. Поэтому родитель ставится только когда объекты есть
  (`engine/code_origin.py`): `git fetch --depth=200 <источник> <sha>` в приватный репозиторий
  (локальный путь отдаёт коммит по sha и в протоколе v2, и в v0; на стороне оператора работает
  upload-pack, который только читает), при неудаче `--depth=1`, обе попытки в одном бюджете 30 с
  (§11); иначе база — корень с причиной. Глубина и таймауты — константы модуля, не поля Settings: они не меняют результат.
- **Сайдкар** `RUN_DIR/code/origin/<sha>.pack`: коммит-родитель и те объекты его дерева, которых нет
  в дереве базы (зафиксированные версии отредактированных файлов — килобайты; предел 64 МиБ). Зеркало
  прогона его копирует (пропускает только `code/repo.git` и `code/worktrees`), поэтому восстановление
  без репозитория оператора пересобирает **тот же id базы**; с репозиторием история дотягивается
  заново. `sync_run` теперь строит все базы линии, а не только те, на которых лежат несобранные
  попытки — после восстановления до разворачивания бэкапа агентов.
- **Детерминизм по версии.** Решение читается из журнала: первая записанная строка `code_snapshot`
  версии 1 (все прогоны до 2026-10-16) — корень, и старый прогон пересобирает свою историческую базу
  байт-в-байт (тест сверяет с алгоритмом версии 1); версии 2 — `base.origin_parent` (или его
  отсутствие). Прогон без единой записанной строки (до doc 79 или убитый до первой записи) решает
  собственная запись решения `code/origin/decision.json` (или сайдкар коммита старта), и только
  без неё — пробой источника, как живой движок (§11). Диагностика решения — `base.origin` на строке, построившей базу
  (`status`, `via: fetched|sidecar|present`, `depth`, `history`, `sidecar`, либо `reason`).
- **Где база остаётся корнем:** закреплённый `seed_base`; несколько редактируемых или один под
  именем; источник не git; **редактируемый — подкаталог репозитория** (монорепо); коммит источника
  не найден; объекты не получены. Монорепо отложено сознательно: база «HEAD с заменённым
  подкаталогом» осуществима, но тогда пути приватного репозитория получили бы префикс, который должны
  разделять коммиты попыток, оверлеи worktree/патчей, экспорт и полоса upstream — слишком инвазивно
  ради истории; корректность не страдает, у такой базы просто нет родителя.

**`_seed_base_of`** (`code_worktree.py`) идёт по цепочке первых родителей, а не `--topo-order`:
тот выдавал сторону второго родителя merge-коммита первой, и старт на слиянии узла A (база X) с
узлом B (база Y) давал базу Y — оверлей сравнивался не с той базой (регрессионный тест с двумя
базами и merge).

**Merge-родители — только честные.**

- Ансамбль, merge-оператор, inject с `parent_ids`: у коммита попытки ОДИН git-родитель (база), а
  остальные родители названы трейлером `Looplab-Co-Parents: n3=<commit>, n5` (коммит — последняя
  записанная попытка этого узла до засева; строка `code_snapshot.co_parents`). Синтезированный merge
  сказал бы `git merge`, что другая ветка уже влита, хотя её изменение могло быть отброшено.
- Настоящий merge: агент в worktree от `node:A` выполнил `git merge nodes/nB` и подал
  `code_from: {"worktree": …}`. Приём штампует голову worktree в `inject_node.code_commit` (присланный
  клиентом — отказ `code_commit_forged`), движок переносит её в `node_created.code_commit`, и коммит
  попытки получает дополнительных родителей — коммиты попыток узлов, достижимые из этой головы
  (`code_identity.py::merged_node_commits`: независимые вершины `merge-base --independent`, каждая
  перепроверена `merge-base --is-ancestor`, не больше 16); первый родитель остаётся базой, так что
  обходы по первому родителю приходят на неё. Строка `code_snapshot.merge_parents`, трейлер
  `Looplab-Merged-Nodes`. После этого `git merge nodes/n<C>` в свежем worktree от базы приносит оба
  изменения, а от `node:A` — fast-forward.

**Экспорт** не меняется: шаг `base` и так дельта «записанный коммит источника → засев», что теперь
ровно `git diff <родитель базы> <база>`; шаг узла берёт базу из строки (или первого родителя).
**Бэкап агентов**: scratch-хранилище получает тот же срез shallow, иначе `bundle create` на
неглубокой истории падает; индекс бэкапа несёт срез, восстановление кладёт его обратно.

Проверка — `tests/test_code_identity.py`: база с родителем и история оператора в worktree,
неизменность `.git` оператора, `git diff HEAD base` = некоммитнутая правка; пересборка той же базы с
репозиторием оператора и без него; бэкап/восстановление неглубокого репозитория; версия 1
воспроизводит корневую базу; `_seed_base_of` на merge; настоящий merge — родители [база, A, B],
ансамбль — трейлер и один родитель.

## 11. 2026-10-16: ревью ядра — решённый id не сдвигается, источник только читается

Проверка — `tests/test_code_identity_hardening.py` (реальный git; каждый тест гоняет поведение).

- **Решённый родитель без объектов.** Журнал решил родителя X, а пересборка не может получить ни
  репозиторий оператора, ни сайдкар: раньше база молча становилась КОРНЕМ с другим id, и каждый id в
  журнале и в экспортированных ветках называл коммит, который пересобранный репозиторий не может
  произвести. Перепроверено (git 2.43): срез shallow на отсутствующем X по-прежнему ломает `log`,
  `rev-list`, `bundle`; срез на САМОЙ базе — нет (`log`, `rev-list`, `fsck` проходят). Поэтому база
  пишется с тем же родителем X (тот же id: `hash-object`, байт-в-байт то, что пишет fast-import,
  — тест сверяет) и становится собственным срезом; `base.origin.via = "cut"`, а `code-status`
  показывает у базы `history: unavailable` (`origin_objects_missing`).
- **Решение без строки журнала.** `sync_run` событий не пишет, поэтому прогон без записанной строки
  (`code_snapshot` не дописан, или только офлайн-синк) после восстановления зеркала пробовал ушедший
  источник и писал корень раньше, чем читал сайдкар. Теперь первая сборка записывает решение в
  `code/origin/decision.json` (зеркало его переносит), а старый прогон без файла читает решение из
  сайдкара коммита старта. Порядок: первая записанная строка, файл решения/сайдкар, и только потом
  пробой источника.
- **Сайдкар чистого checkout.** Сайдкар вычитал и КОРНЕВОЕ дерево базы; при дереве засева, равном
  дереву HEAD, в паке оставался один коммит, пересборка (она читает пак ДО записи базы) видела
  `sidecar_incomplete`. Корневое дерево родителя теперь в паке всегда. `rev-list --objects
  --no-object-names`: путь с `\r` больше не расщепляет строку.
- **Версия прогона.** `run_version`: версия первой строки `code_snapshot` ЛЮБОГО статуса; без строк —
  метка репозитория `looplab.identityVersion` (пишется при создании; репозиторий с базами без метки —
  версия 1); иначе текущая. Новые строки возобновлённого прогона версии 1 штампуются 1, а не версией
  сборки. Невоспроизводимый остаток назван в докстринге: экспорт офлайн-синка прогона до doc 79,
  чей репозиторий затем потерян.
- **Стоимость на пути оценки.** История выкачивается ДО `repo.lock()` (`prepare_first_base`), обе
  глубины — в одном бюджете `FETCH_BUDGET_S = 30` с; один раз на прогон (база, файл решения и
  сайдкар — её долговечный результат). `CodeRepo.add_shallow` пишет под собственным `shallow.lock`
  git, так что fetch вне блокировки не теряет срезы.
- **Источник только читается — кем бы он ни владел.** Глобальный конфиг герметичного git — /dev/null,
  поэтому `safe.directory` оператора не читался, и источник другого uid давал «dubious ownership»,
  который сообщался как «не git». `code_repo.py::readonly_git` / `CodeRepo.fetch_readonly` передают
  `safe.directory` для пути и его предков (не `*`), а `upload-pack` получает их в собственной
  командной строке: локальный транспорт сбрасывает `-c` (`GIT_CONFIG_PARAMETERS`) — замерено. `~`
  раскрывается везде; «подкаталог» решает `os.path.samefile` (регистр macOS). Корни, куда нельзя
  ставить worktree, дополнены правилом обнаружения git (ближайший предок с `.git`).
  Остаток вне этого изменения: отпечаток рабочего пространства на старте (`run_started.workspace`)
  для источника другого uid по-прежнему пишет `hash:`, поэтому база такого прогона — корень.
- **Экспорт.** Удаление и «уже есть» сравнивают содержимое, режим — отдельно. Режим засева
  переносится, только если ни цель, ни ИСТОЧНИК не говорят `core.fileMode=false` (vfat/NTFS/CIFS/9p/
  `/mnt/c` дают 0755 всем файлам — раньше это был массовый `chmod +x`); иначе берётся режим коммита
  источника, новый файл — 100644. Отчёт: `file_mode {trusted, target, source}`.
- **Старт worktree/патча** — только коммит прогона (первородительская цепочка доходит до базы); коммит
  истории оператора — `code_start_not_run_commit` (оверлей считался бы от него и откатывал
  некоммитнутые правки базы). Место по умолчанию не может быть ссылкой (`code`, `code/worktrees`, сам
  путь) — иначе `git worktree add` писал туда, куда она указывает.
- **Merge-родители — только за код, который есть.** Голова worktree штампуется, только если дерево
  подачи равно дереву HEAD; с некоммитнутыми правками git-родителей нет (`head_commit_withheld`).
  Жизненный цикл после eval-сброса берёт `code_commit` предыдущего `node_created`, если оверлей тот же
  (сравнение по содержимому). Записанная голова, которой нет в репозитории (пересборка до
  восстановления бэкапа агентов), — попытка не строится (`merge_head_missing`), а не пишется без
  родителей. Независимые вершины — один `rev-list --stdin`, а не argv из всех id (Windows).
- **Чужая ветка.** Merge base ищется в чужом репозитории (или в источнике), где есть оба коммита, —
  только чтение; в приватный репозиторий едут два коммита глубины 1. Раньше — вся история без
  `--depth` под блокировкой прогона и merge base в неглубоком (v2) репозитории: ветка, ответвлённая
  до среза, отказывалась. Иначе — ограниченное углубление (`FOREIGN_DEEPEN_ROUNDS` × `HISTORY_DEPTH`),
  отказ называет предел. `git.repo` может быть подкаталогом (fetch идёт из верха) и мелким клоном.
- **Одно правило на одно понятие.** `code_repo.py::is_object_id` (40 или 64 hex) во всех местах ядра,
  `code_origin.py::run_source` — единое чтение источника для родителя базы, экспорта и merge base,
  `CodeRepo.fetch_readonly` и `CodeRepo.commit_tree` (фиксированная личность — те же id, тест).
