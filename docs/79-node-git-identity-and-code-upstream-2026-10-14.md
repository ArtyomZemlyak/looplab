# 79. Git-идентичность попыток, фактический конфиг и доставка кода в репозиторий задачи (2026-10-14)

*EN summary: every evaluated attempt becomes a commit of a run-owned private git repository (not a
worktree of the operator's repo), its effective hyperparameters are recorded and checked against the
declared ones, external agents get worktrees/patch intake over that repository, and the run's fixes
export into the task repository as a new branch. Revisits doc 37 with a measurement.*

**Статус (2026-10-14): реализовано, тесты `tests/test_code_identity.py`; живой GPU-прогон с
включённой записью ещё не проводился (см. §9).** Операторский путь — [guide/code-identity.md](guide/code-identity.md).

## 1. Проблема

Запрос оператора: «лучшие наработки и фиксы со всего рана должны стекать в репу; git worktree».
Ночь 2026-10-13/14 показала, почему этого не происходило:

- Узлы работают на материализованных копиях (doc 37), а дифф узла — это `node.files`, не коммит.
  Ни одна попытка не имела git-идентичности, по которой её можно отревьюить или вмержить.
- Внешний агент (Codex) правил код не через узлы, а в некоммитнутых копиях источника
  (`/dev/shm/two-stage-*/repo`, не git). Фикс LR-warmup лежал коммитом `a92ba534a` в отдельном
  worktree, two-stage guard и фикс `max_steps` — только в копиях. В ветку задачи не попало ничего.
- Полоса upstream (doc 72 §18, doc 73 §2) двигает базу внутри прогона, но выхода в репозиторий
  задачи у неё не было (doc 72 §19, O14), а для внешних прогонов без блока `upstream` она не работает.
- Doc 77 §1–§2: неизвестно, какой код фактически исполнялся и с какими lr/batch/seed/steps — у узлов
  было `applied_params={}`, реальные числа жили только в логе стадии и во внешнем `protocol.json`.

## 2. Решение и замер против doc 37

Doc 37 отклонил `git worktree` **исходного репозитория** для рабочих каталогов узлов по двум
дисквалифицирующим причинам: (§5c) рабочее дерево подключено к объектной базе оператора, и
`git add -A` в узле затягивает туда гигабайты чекпойнтов; (§5d) worktree засевает HEAD, а не
рабочее дерево оператора — на v1 10 из 17 файлов были бы не те. Обе причины остаются в силе,
поэтому решение doc 37 для **рабочих каталогов узлов не меняется**: узел исполняется на копии.

Новое: **git-идентичность даётся не рабочему каталогу, а попытке** — дешёвым эквивалентом
worktree. У каждого прогона свой приватный bare-репозиторий `RUN_DIR/code/repo.git`:

- **базовый коммит** на каждый архив засева (`base_snapshots/<digest>`) — дерево ровно из
  архива, т.е. рабочее дерево оператора с некоммитнутыми правками и неотслеживаемым скорером
  (закрывает doc 37 §5d);
- **коммит попытки** на каждую материализацию жизненного цикла узла — база + оверлей, прочитанный
  с диска после материализации; родитель — база, на которой узел засеян. `git show` коммита =
  ревью изменения узла. Ремонт внутри цикла даёт второй коммит поверх первого.
- Репозиторий приватный: объектная база оператора недоступна по построению (закрывает doc 37 §5c).
  Worktree выдаются только внешним агентам и только из этого репозитория (§4).

Замер (`benchmarks/node_git_identity_cost.py` на клоне MiniOneRec `work-train`, 741 файл,
13.8 МБ; tmpfs, 7 повторов, медиана):

| операция | время | примечание |
|---|---|---|
| засев копией (как сейчас) | 0.064 с | на каждый узел, не меняется |
| `git worktree add`+`remove` исходного репо (арм doc 37) | 0.096 с | отклонён по §5c/§5d |
| базовый коммит из архива (fast-import) | 0.60 с | один раз на базу |
| коммит попытки, 1 файл (env-оверлей) | 0.0075 с | чистый fast-import |
| полная запись попытки (`record_attempt`, на архиве живого g-v3) | 0.026 с | lineage, ref, diffstat |
| коммит попытки, 20 файлов | 0.028 с | |
| worktree агента из приватного репо | 0.097 с | только по запросу (§4) |
| размер репо: база / +50 попыток | 9.56 МБ / 10.38 МБ | ~16 КБ на попытку |

На фоне оценки узла (часы на GPU) запись попытки — 26 мс; одноразовая база — 0.6 с. Дисковая цена —
сжатая копия базы (~70 % архива засева) плюс килобайты на попытку.

## 3. Запись в журнале и репозитории

- `code_snapshot` (DIAGNOSTIC, fold его не читает, fence-нейтрален) — `{node_id, generation,
  seed_event_seq, commit, base{digest,commit}, changed[], stats, source, status}`; пишется
  `engine/code_identity.py::record_materialized` из `WorkspaceSeeder.materialize` для собственного
  каталога узла (канарейка и confirm — тот же код, не новая попытка) и
  `record_after_terminal` после терминала, если оверлей изменился в ходе оценки (ремонт).
- Ссылки: `refs/heads/base` (активная база), `refs/looplab/bases/<digest>`, `refs/heads/nodes/n<id>`,
  `refs/looplab/attempts/n<id>/g<gen>/s<seed_seq>[-repair]`, `refs/heads/champion`, `agent/<name>`.
  Ссылка ремонта — соседняя, не вложенная: git не может держать `…/s5` и `…/s5/repair` сразу.
- Линия баз (`base_lineage`): первая база — корень; база из `base_advanced` — дочерняя к
  заменённой (с предложением, узлом-источником, флагом и gate-доказательством в трейлерах);
  новый дайджест без продвижения — `source_changed` (оператор поменял источник посреди прогона).
  Кандидатные засевы полосы (`workspace_seeded` без узла) базой не считаются, пока нет продвижения.
- Детерминизм: фиксированная идентичность и время события → те же входы дают те же id коммитов.
  Старые прогоны: `sync_run` строит те же коммиты из журнала (`source: "log"`), событий не пишет.
  Попытка — только засев собственного каталога узла (`code_identity.py::lifecycle_seeds`):
  `workspace_seeded.workdir` отличает его от канарейки, confirm и noise floor; в старом журнале без
  этого поля берётся первый засев жизненного цикла.
- Сбой git или архива — запись `status: unavailable` с причиной, никогда не отказ оценки.

## 4. Внешние агенты

Три способа подать код, все сводятся к обычному оверлею `inject_node`:

1. `files`/`deleted` — как раньше.
2. Worktree от LoopLab: `looplab code-worktree RUN name` или `POST /api/runs/{id}/code/worktrees` →
   `RUN_DIR/code/worktrees/<name>` на ветке `agent/<name>` от активной базы (или `node:<id>`). Агент
   правит, запускает, коммитит; `inject_node` с `code_from: {"worktree": name}` превращает
   «база засева → текущее состояние» (коммиты, некоммитнутые правки, новые файлы) в оверлей. От
   `node:<id>` это изменение самого узла плюс правки агента: оверлей материализуется поверх базы,
   а не поверх узла (`code_worktree.py::_seed_base_of`). Путь вне поверхности, который агент оставил
   как в стартовом коммите (актив задачи), не отказ, а наследство (`inherited_outside_surface`).
3. Патч: `code_from: {"patch": "<unified diff>", "start": "base"}`.

Оверлей проверяется той же `SurfacePolicy`, что и полоса upstream (поверхность правки и защищённые
файлы), и её же лимитами (128 путей, 2 МиБ текста). `POST /code/overlay` — предпросмотр без
отправки; ответ говорит `stale_base`, если worktree начат не от текущей базы. Источники не в git
получают git-снимок автоматически: базовый коммит строится из архива засева, а не из git источника.

## 5. Экспорт в репозиторий задачи

`looplab code-export RUN --repo <task-repo> [--branch] [--onto] [--prefix] [--node champion|N|none]
[--patches DIR] [--dry-run]` создаёт **новую ветку** (по умолчанию `looplab/<run_id>`):

1. `base` — код, с которого стартовал прогон. Если коммит источника, записанный в `run_started`,
   есть в целевом репо, это ДЕЛЬТА «этот коммит → засев» (только некоммитнутые правки), наложенная
   на `--onto` по путям с трёхсторонним слиянием — поэтому второй прогон, экспортированный поверх
   ветки первого, не откатывает его изменения. Иначе (источник не git) цель приводится к байтам
   засева по каждому его пути. `--onto` по умолчанию — тот же записанный коммит, иначе HEAD.
   Удалений шаг не делает: путь, которого нет в снимке, считается (`not_in_snapshot`).
2. `upstream` — каждое продвижение базы полосой, с доказательством гейта в трейлерах.
3. узел — изменение чемпиона (или указанного узла) с метрикой. Только коммит ЭТОГО жизненного
   цикла (записанный или построенный `sync_run`); без него шаг пропускается — ветка `champion`
   может указывать на прежнего чемпиона и запасным вариантом не служит.

Записанный коммит источника — только у `editable:` (корневого, иначе общий для всех именованных),
никогда у `data:*`/`ref:*`. Префикс по умолчанию читается через адаптер задачи (`repo`,
`editable_path`, `editables`, `~`): корневой редактируемый определяет его; только именованные —
общий каталог P с `P/<имя>` у каждого, иначе отказ `export_prefix_ambiguous` до `--prefix`.

Механика: plumbing во временном индексе (`hash-object`, `update-index`, `write-tree`, `commit-tree`),
затем `update-ref` новой ветки с нулевым старым значением. HEAD, индекс, рабочее дерево, другие
ветки, remotes и конфиг оператора не трогаются; push не выполняется никогда. Путь применяется,
если в цели старые байты прогона (или уже новые); иначе — текстовое трёхстороннее слияние
(`git merge-file`); конфликт останавливает экспорт до этого коммита и называет пути.
`--patches` дополнительно пишет серию `format-patch` для merge request.

## 6. Фактический конфиг (doc 77 §2)

`core/effective_config.py::capture` на чтении метрики собирает значения в канонических ключах
(`lr`, `batch_size`, `micro_batch_size`, `grad_accum`, `world_size`, `seed`, `max_steps`, `epochs`,
`warmup_steps`, `warmup_ratio`, `scheduler`, `weight_decay`) из трёх именованных источников:
окружение, переданное командой оценки (без секретов), `KEY=VALUE` env-файлов оверлея и дампы конфига
в логах стадий (`LR: 2e-4`, `Batch: 1024 (micro=128)`, `SFT_LEARNING_RATE=…`). Объявленные
`Idea.params` сверяются: `checked` — значение совпало, `mismatches` — наблюдались другие, `unknown` —
ничего не наблюдалось (не ноль и не согласие); префикс `stage2_` ограничивает сверку логом стадии.
Два разных значения в одной стадии — `conflicts`. Событие `effective_config` (DIAGNOSTIC) пишется
после терминала. На логах живого g-v3: `lr=2e-4, batch=1024, world=8, epochs=1` по обеим стадиям,
`stage2_lr` проверен, `stage2_warmup`/`steps`/`seed` — `unknown` (guard печатает их без разделителя).

## 7. Вид оператора: что ждёт upstream

`GET /api/runs/{id}/code` и `looplab code-status RUN` — одна проекция (`code_status`, только чтение):
базы с причиной и доказательством, попытки (коммит, изменённые пути, метрика, статус, чемпион,
фактический конфиг и расхождения), `upstream.proposals`/`in_flight` с узлом-источником, его метрикой
и последним вердиктом гейта (проверки, дельта, число исполнений), `nominations` (непродвинутые
capability-ханки измеренных узлов), а для прогонов без полосы — `unlaned_changes`: измеренные
попытки, менявшие код, а не только рецепт. `GET /code/diff?commit=` — ограниченный дифф коммита.
Поля простые (строки/числа/списки) — UI-ветка может показать их в Inspector (SourceSnapshotPanel /
RuntimeSnapshotPanel из doc 77).

Полоса upstream (auto/propose/off) не изменена: она по-прежнему продвигает базу только через
измеренный гейт; новые базы автоматически становятся коммитами ветки `base`, а `code-export`
переносит их в репозиторий задачи.

  неотслеживаемым скорером — база содержит рабочее дерево, у попытки коммит, репозиторий оператора не

  сверка объявленных параметров; **сквозной случай**: узел 0 чинит баг пайплайна (ремонт), полоса
  propose → реальный гейт (9 исполнений) → advance, узел 1 засевается на новой базе и проходит,
  экспорт создаёт ветку `base`(пусто) → `upstream`(фикс) → узел; конфликт на сдвинутой цели;
  два прогона одного task repo доставляются последовательно (B поверх ветки A сохраняет A);
  внешний агент: worktree → коммит + некоммитнутая правка → оверлей, отказ на защищённом скорере,
  патч, все HTTP-маршруты, `code_from` в `inject_node`.
- Реальные данные (копия журнала и архива живого `minionerec-two-stage-warmup-g-v3-20261014`,

- Живой GPU-прогон с записью `code_snapshot` ещё не делался; запись — 26 мс на попытку, но первая
  база большого репозитория (≤64 МиБ, предел архива) — секунды, на потоке подготовки каталога.
- ~~Оверлей worktree — только текст UTF-8~~ — закрыто 2026-10-14: бинарный файл из worktree или

  который материализация разворачивает со сверкой хеша (`code_worktree.py::store_blob`,
  `tests/test_binary_overlay.py`); ≤32 МиБ на файл, ≤64 МиБ на оверлей.
- Полоса upstream для внешних ранов без блока `upstream` умолчаний не получает (гейт без
  объявленных проверок ничего не проверяет). Вместо этого `code_status.upstream.readiness` перечисляет
  недостающие обязательства (`seed_base`, `eval.scorer_boundary`, `upstream`, `upstream_mode`,
  `trust_mode`) с примером объявления и напоминает, что `code-export` доставляет фиксы и без полосы.
- Сквозной многостадийный «GPU-подобный» прогон на CPU-заглушке (prepare→train→score, пул из двух
  фиктивных устройств, коммит на каждую попытку, фактический конфиг из лога train) —
  `tests/test_code_identity_multistage.py`.
- Экспорт не удаляет файлы на шаге `base` и не переносит переименования как rename (diff без
  rename-детекции); конфликт решает человек по названным путям. Проверки целевой ветки после
  экспорта (тесты task repo) — шаг оператора/интегратора, LoopLab их не запускает.
- Переход внешних агентов на worktree/`code_from` — изменение их инструкций (AGENTS.md агента).
- Doc 77 §1 SourceSnapshotPanel и §2 RuntimeSnapshotPanel в UI — за UI-веткой; данные есть.
