# 73. Узлы без обязательной оценки и автоперенос кода в базу — анализ, критика, план (2026-10-07)

Два запроса оператора от 2026-10-06, оба из прогонов `minionerec-*`:

1. **Узел не обязан быть оценкой.** Ассистент или кто угодно должен в любой момент мочь
   сделать узел, который, например, готовит датасет для следующих десяти узлов. Ожидаемая
   оценка может меняться, и оценок может быть несколько («это отдельный трек»). Хотя проверки
   дрейфа, скорее, — отдельный прогон со своей оценкой.
2. **Перенос кода в базу — по умолчанию и в фоне.** Где-то поправился баг → фикс уходит в
   базу, и всем текущим Developer-агентам приходит принудительный хинт. Новый лучший вариант
   с кучей кода → отдельный воркер сразу вносит его в базу. Все агенты знают, что сейчас
   происходит. По умолчанию включено, настраивается просто.

Ниже по каждому: что есть сейчас, варианты, критика, рекомендация, этапы. В конце — что
нужно решить оператору.

## 1. Узлы без обязательной оценки

### 1.1 Что есть сейчас

- Каждый узел проходит один путь: идея → сборка → конвейер стадий → `score` → **ровно один
  терминал** (`node_evaluated` | `node_failed`, инвариант 2). Узел без метрики — это провал.
- Общие данные между узлами идут только через `data:` оператора (монтирование) или через
  абсолютный путь, вписанный в идею вручную.
- Переиспользование стадий **между** узлами измерено и **отвергнуто**: кеш стадий оказался
  примитивом порчи (`runtime/stage_identity.py`, `looplab stage-dups`). Переиспользование
  внутри узла после пересборки выключено (doc 68 68.3e: повторно запущенный жизненный цикл
  оценил чекпоинт, которого не было).
- С 2026-10-07 есть `eval.parent_workdirs_env` (doc 73 не вводит, а опирается на него): оценка
  узла может узнать абсолютные каталоги родителей и читать их; запись в каталог прогона
  по-прежнему запрещена.
- Дополнительные метрики: `eval.metrics` (объявленные), `metric_retarget`, с 2026-10-07 —
  `looplab import-metrics` (значения, измеренные после прогона, рядом с живыми).

### 1.2 Варианты

**A. Узел-артефакт (`kind: artifact`).** Узел строится и исполняет свои стадии, но вместо
`score` объявляет **выходы** (каталог/файлы). Терминал — новый `node_produced
{outputs: [{path, sha256, bytes}]}`, третий допустимый терминал. Выходы после терминала
делаются только для чтения. Потребитель объявляет `uses: [node_id]`; движок монтирует
`./uses/<id>/` только на чтение, сверяет дайджесты при материализации и пишет их в терминал
потребителя. Узел-артефакт не ранжируется, не участвует в плато, его секунды идут в
отдельную корзину `prep`.

**B. Версия данных как операторский объект.** Команда «опубликовать датасет» кладёт каталог
в `<run>/data/<name>@<n>` и добавляет его как ещё одно монтирование для будущих узлов. Узла
нет.

**C. Вернуть кеш стадий между узлами.** «Подготовку данных» один раз, остальные узлы
переиспользуют стадию по ключу входов.

**D. Треки оценки (`eval.tracks`).** Дополнительные объявленные оценщики
(`{"drift_w07": {"command": [...], "metrics": {...}}}`), запускаемые по команде
`evaluate_track {node_id, track}` над **сохранёнными артефактами** уже оценённого узла.
Результат ложится в объявленные доп. метрики с каналом `declared` и именем трека.

### 1.3 Критика

| | За | Против |
|---|---|---|
| A | Точно моделирует запрос: любой (ассистент, оператор, Researcher) создаёт узел подготовки; у артефакта есть сборка, ремонт, трассировка, провенанс; потребление — явное и проверяемое | Самое глубокое изменение: новый терминал трогает свёртку, ledger карточек, выбор, UI, отчёты. Риск «загрязнить» ранжирование узлом без метрики; нужен реестр видов узлов и проверка каждого читателя |
| B | Просто, не трогает инварианты узлов | Подготовка датасета — это код, который надо написать, починить и пересобрать; без машинерии Developer/ремонта это ручная работа оператора. Нет связи «этот датасет сделал вот этот код» |
| C | Дёшево по коду | **Уже измерено и отвергнуто** как примитив порчи. Не возвращаем |
| D | Закрывает «много оценок» и дрейф без новой модели узла; переоценка @200 старых узлов — тот же механизм | Нужна гарантия, что артефакты узла целы и принадлежат его последнему жизненному циклу (штамп манифеста + терминал поколения) |

Отдельно про дрейф. Оператор прав: недельные проверки дрейфа — это **отдельный прогон** со
своей задачей («оценить чекпоинты X на неделях w00…w07»). Внутри поискового прогона они
смешали бы две цели. Но механизм D в отдельном прогоне и есть такой прогон: задача —
оценщик, узлы — `evaluate_track` над импортированными (`seed_from_run`) артефактами.

### 1.4 Рекомендация

**D, затем A.** C не делаем, B не нужен при наличии A.

- **Этап 1 — треки оценки (D).** Самая большая польза при наименьшем риске: дрейф, @200,
  «другая оценка» решаются без новой модели узла. Терминал узла не меняется; трек пишет
  отдельное событие `track_evaluated {node_id, generation, track, metrics, eval_seconds}`,
  которое свёртка кладёт в доп. метрики с пометкой трека. Предусловие исполнения: узел
  оценён в текущем поколении, штамп манифеста рабочего каталога совпадает, каталог не
  пересобирался после терминала. Иначе отказ с причиной.
  *Отгружено 2026-10-07 в облегчённом виде:* `eval.tracks` + `looplab evaluate-track` при остановленном движке, запись через `extra_metrics_imported` (источник `track <name>`), отказ ноде с чужим штампом манифеста. Команда движка `evaluate_track` для живого прогона — следующий шаг.
- **Этап 2 — узлы-артефакты (A).** *Отгружено 2026-10-07 в облегчённом виде:* `inject_node` с `node_kind: "artifact"` и `uses`, поля на `node_created`/`Node`, а не на `Idea` (её JSON-схема уходит модели Researcher — поле изменило бы промпт каждого прогона); успех = классификатор `no_metric`, метрика артефакта всегда None; proxy/ASHA/плато его не трогают; `uses` только на уже произведённые артефакты (без гонки потребителя и производителя). Терминал остаётся `node_evaluated` — третий терминал не понадобился. После ревью: артефакт не ранжируется и под `metric_retarget` (свёртка, `replay.py::_apply_objective`), не считается «неранжированным» в `objective_coverage`, не проходит metric salvage, а пересборка (`node_reset` из implement) сохраняет `node_kind`/`uses`. Researcher пока артефакты не создаёт. *Дополнено 2026-10-08:* под `Settings.researcher_artifacts` (по умолчанию выключено, закреплено в снапшоте) Researcher видит в схеме эмита `node_kind`/`uses` и список «PRODUCED ARTIFACTS» (`agents/artifact_ideas.py`); поля едут на `Idea` (скрыты из схемы и опускаются при сериализации, когда пусты), свёртка делает узел артефактом и оставляет в `uses` только реальные артефакты. Исходный план этапа:
- С ограничениями:
  - вид узла — поле `Idea.kind ∈ {experiment, artifact}`, по умолчанию `experiment`; старые
    журналы сворачиваются как раньше;
  - `node_produced` регистрируется третьим терминалом в инварианте 2, `fold` идемпотентен;
  - выходы неизменяемы (hardening + дайджест), потребление — только явное `uses`, дайджест
    проверяется при каждой материализации потребителя; несовпадение — отказ, а не подмена;
  - узел-артефакт исключён из `feasible_nodes`, выбора чемпиона, плато, `systemic_failure_stop`
    и `mislead_gap` — по реестру видов, а не по разбросанным проверкам.
- Создавать узлы обоих видов может кто угодно: команда `inject_node` с `kind`/`uses`,
  инструмент ассистента, Researcher (через `RESEARCHER_ACTION_ATTRS`).

### 1.5 Риски этапа 2

- Читатель, который считает «узлы» и не знает про вид, начнёт учитывать артефакты (бюджеты,
  счётчики, отчёты). Защита — реестр видов + тест, что каждый читатель `evaluated_nodes()`
  и `feasible_nodes()` отфильтрован (по образцу `engine/attribute_sites.py`).
- Узел-артефакт, чьи выходы зависят от undeclared внешнего состояния (сеть, мутирующий
  датасет), невоспроизводим. Это фиксируется в квитанции, но не предотвращается.

## 2. Автоперенос кода в базу

### 2.1 Что есть сейчас (doc 72, §18)

Полоса upstream реализована, но **ручная по замыслу**: пауза → предложение Maintainer →
измеренные проверки (эквивалентность, регрессии, repair-probe) → явный `advance` (CAS) →
отдельный resume. В doc 72 прямо записано «No automatic advancement». Причина — контракт
оценки: при тренере и скорере в одном файле тихая смена базы посреди прогона может
незаметно поменять саму метрику, и узлы до и после станут несравнимы.

Предусловия полосы: `seed_base`, объявленная `cmd.scorer_boundary`, операторские тесты и
регрессии, `trusted_local`, самодостаточный командный оценщик. Docker, хостовый скорер,
`run_setup` и GPU-проверки этой приёмкой не покрыты (§18.4). В `minionerec-backbones-v11`
блока `upstream` нет, поэтому полоса там недоступна.

### 2.2 Чего хочет оператор и где это ломается

| Желание | Почему нельзя «просто включить» |
|---|---|
| Фикс бага → сразу в базу | Если фикс задел общий раннер, а раннер = скорер, следующие узлы оцениваются уже другим кодом. Нужна граница скорера и проверка «старый рецепт падал, новый проходит» |
| Новый чемпион → воркер вносит всё в базу | Код чемпиона — это и РЕЦЕПТ (его научная ручка), и ВОЗМОЖНОСТЬ (общее улучшение). Внести рецепт в базу — значит сделать его поведением по умолчанию для всех следующих узлов; это меняет науку поиска, а не чинит код |
| Без паузы | Полоса сейчас требует остановленного движка для CAS. Нужна гарантия: узел, материализованный до смены базы, доживает на своей базе (включая ремонт) |
| По умолчанию | Прогоны без объявленной границы скорера не могут пройти ни одной проверки — «auto» там должен честно деградировать, а не молча работать без защиты |

### 2.3 Предложение

Одна настройка `Settings.upstream_mode ∈ {auto, propose, off}`.

- **auto** — три трека ниже работают сами, при условии, что у задачи есть блок `upstream`
  (граница скорера + тесты). Если его нет, режим работает как `propose`, и в UI и брифе это
  сказано.
- **propose** — кандидаты находятся и проверяются автоматически, но `advance` — одной кнопкой
  (или командой ассистента).
- **off** — как сейчас.

**Трек 1 — раскатка фикса.** Триггер: ремонт узла изменил файлы вне рецепта узла и вне границы
скорера, и узел после ремонта оценён. Проверки: операторские тесты, repair-probe (старый
рецепт падает на исходном триггере, новый проходит) и неизменность байтов скорера. Полное
повторение оценки не требуется: у старого рецепта не было метрики, сравнивать нечего. Итог —
`base_advanced {reason: repair}`. Сразу после — **хинт Developer-агентам** всех узлов в
работе и всех будущих ремонтов: «в базе R исправлено X (файлы, суть); если твой узел падает
на этом — подтяни». Researcher хинт не получает.

**Трек 2 — интеграция чемпиона.** Триггер: новый чемпион. Фоновый воркер Maintainer в своём
git worktree, без паузы прогона, делит дифф на рецепт и возможности. В базу идут
**только возможности, за флагом с прежним поведением по умолчанию**; рецепт остаётся у узла.
Проверки — как в doc 72: эквивалентность (флаг выключен → старый результат воспроизводится),
регрессии, неизменность скорера. Стоимость на GPU — повторные оценки. Варианты: полные
повторы (дорого, строго) или канарейка на срезе (дёшево, слабее). Это решение оператора (§2.6).

**Трек 3 — общая доска.** Свёрнутая проекция `upstream_board`: ревизия базы, последние
продвижения с причинами, работа в процессе («интегратор вносит возможности чемпиона #37»,
«фикс из узла 12 на проверке»). Developer видит подробно, Researcher — одной строкой. Это
изменение промпта, поэтому флаг `upstream_board_brief`: включён для новых прогонов, для
возобновлённых старых — строка `LEGACY_CONFIG_SNAPSHOT_DEFAULTS` = off.

**Без паузы.** Для этого каждый жизненный цикл узла закрепляет ревизию базы при
материализации — `base_revision` уже пишется на `workspace_seeded`, и это нужно сделать
источником истины. Ремонт продолжает работу на закреплённой ревизии, следующий жизненный
цикл берёт текущую. CAS на `base_advanced` выполняет главная задача движка после того, как
фоновый воркер вернул результат (инвариант 1: фоновые задачи возвращают значения, пишет
главная).

### 2.4 Критика собственного предложения

- **Трек 2 спорен по сути.** «Внести всё лучшее в базу» превращает поиск из дерева в
  цепочку: следующие узлы стартуют с кода чемпиона, а значит меньше разнообразия и больше
  риск застрять в локальном оптимуме. Поэтому в базу идут только возможности, и только за
  флагом с прежним поведением: дерево остаётся деревом, а пользоваться возможностью или нет,
  решает рецепт узла.
- **Стоимость GPU-проверок реальна.** Эквивалентность на полном обучении 1.5B — это часы.
  Без объявленной дешёвой канарейки трек 2 на таких задачах будет либо дорогим, либо слабым.
- **Граница скорера.** В `minionerec` тренер и скорер — один `run_experiment.sh`. Пока скорер
  не вынесен в отдельный файл и не объявлен, трек 1 не может доказать «метрика не
  поменялась», и `auto` честно работает как `propose`. Для v12 скорер (ваш сервис оценки /
  `evaluate.py`) стоит объявить отдельным `scorer_boundary`.
- **Хинт может навредить.** Developer, получивший хинт посреди сборки, может переписать
  работающий код. Поэтому хинт информирует («если падаешь на X»), а не приказывает, и
  доставляется на границе хода инструментального цикла, а не вклинивается в контекст.

### 2.5 Этапы

1. **Доска + хинты** (дёшево, сразу видно). *Отгружено 2026-10-07 в облегчённом виде:*
   `core/upstream_board.py` — одна проекция свёрнутой истории полосы (база, продвижения,
   предложения в работе, итоги); Developer под `Settings.upstream_board_brief` (вкл. для новых
   прогонов, `LEGACY_CONFIG_SNAPSHOT_DEFAULTS` = выкл.) во всех ходах сборки/ремонта видит
   продвинутые возможности с флагом, источником и описанием — через уже привязанную свёртку
   (`bind_state`), без нового канала; `looplab inspect` печатает доску. Researcher свою строку
   уже получал (doc 72). Предложения «на проверке» Developer не показываются — их нет в его коде.
   Исходный план этапа: Проекция `upstream_board`, бриф Developer/Researcher
   под флагом, хинт о `base_advanced` через реестр `engine/signal_delivery.py::SIGNALS`.
   Работает поверх текущей ручной полосы.
2. **Закрепление базы на жизненный цикл + продвижение без паузы.** CAS с главной задачи, тесты
   на «узел до смены доживает на своей базе».
3. **Трек 1 (фиксы)** в режимах `propose`/`auto`.
4. **Трек 2 (чемпион)**, фоновый Maintainer как продюсер в `BACKGROUND_LANE_PRODUCERS`.

Каждый этап проверяется на игрушечной repo-задаче со скорером в отдельном файле (офлайн, без
GPU): фикс в общем раннере → раскатка → хинт → следующий узел стартует с исправленной базы.

### 2.6 Что решить оператору

1. **Умолчание:** `auto` (с честной деградацией до `propose` без границы скорера) или
   `propose` (автоматическая проверка, `advance` одной кнопкой)?
2. **Цена проверки трека 2 на GPU:** полные повторы (строго, часы) или объявленная канарейка
   (дёшево, слабее)?
3. **Минимальный объём:** если нужен быстрый эффект — этапы 1 и 3 (доска + фиксы) дают
   основную пользу, трек 2 можно отложить.

## 4. Что ещё не закрыто из решения оператора — разбор и план (2026-10-08)

Решения оператора (2026-10-05, подтверждены 2026-10-08 «делаем все»): автоматически по умолчанию
(`upstream_mode: auto`), трек 1 — фикс из ремонта в базу **плюс принудительный, ограниченный,
дедуплицированный хинт работающим Developer, записанный событием**; трек 2 — фоновый интегратор
чемпиона с **потолком денег на прогон, лимитом продвижений в час, выключателем и аудитом**; на GPU —
**дешёвая объявленная канарейка по умолчанию и полные повторы по настройке**; никогда не продвигать
патч через границу скорера; доска показывает работу в процессе.

### 4.1 Сверка с тем, что уже в master (строки статуса выше)

| Требование | В master | Чего не хватает |
|---|---|---|
| Автор трека 1 и трека 2 | `engine/upstream_author.py` (`Settings.upstream_author`): источник — отремонтированный узел, затем чемпион; два платных вызова (Maintainer + критик), черновик → обычный propose → gate → advance; `lane_authored` | — |
| Облегчённый гейт для фикса | `upstream.repair_gate: probes` (объявление оператора, `equivalence_waived`) | — |
| Developer на новой базе | `_run_developer` перепривязывает Developer к текущей базе перед каждым вызовом (`rebind_base`) | **хинт сессии, которая уже идёт** (новая база видна только со следующего вызова), и **запись, что кому сказано** |
| Потолки и выключатель | не более 6 черновиков за прогон (`AUTHOR_MAX_PER_RUN`); общий потолок денег прогона | **потолок денег автора в USD** (настройка, расход в журнале), **лимит автоматических продвижений в час**, **выключатель** на живом прогоне |
| Проверка на GPU | полные повторы (`upstream.repeats`) или отказ от повторов для фикса | **профиль `canary` по умолчанию** (одна пара под объявленной `eval.canary`), `full` — по настройке |
| Граница скорера | отказ на сборке кандидата и в каждом исполнении гейта | — |
| Доска / работа в процессе | UI: режим, очередь с квитанциями, строки автора (`upstream_live_view`) | показать в той же проекции выключатель и придержанные шаги |

Мой собственный трек 1 без LLM (детерминированный автор фикса с профилем `identical`) и интегратор
с отдельным слотом сохранены в ветках `wip/upstream-phase1`/`wip/upstream-phase2`, но в master не
идут: они дублируют `upstream_author.py` и `repair_gate: probes`.

### 4.2 План (только недостающее)

1. **Хинт работающим Developer (G1).** После каждого `base_advanced` живого движка главная задача
   пишет `upstream_hint_issued {hint_id, proposal_id, advance_seq, text ≤700, sessions}` (свёрнуто в
   историю полосы; модельный `summary` в ограде `fence_untrusted`) и публикует его на доске
   `engine/upstream_hints.py::UpstreamHintBoard`. `_run_developer` открывает сессию на вызов;
   `agents/tool_loop.py::interjection_scope` отдаёт каждое уведомление циклу как `user`-ход на
   границе хода (≤3 на сессию, каждое один раз); сессия сама пишет диагностику
   `upstream_hint_delivered {hint_id, session, node_id}`. Без сессии — байт-в-байт прежний список
   сообщений. Маршрут `upstream_advance_hint` в `SIGNALS`. Приёмка: e2e на игрушечной задаче — ремонт
   чинит общий раннер, автор (заглушка модели) предлагает, гейт, продвижение, сессия Developer,
   заблокированная посреди цикла, получает уведомление, следующий узел стартует на исправленной базе.
2. **Выключатель, потолки, аудит (G2–G4).** Управляющее событие `upstream_auto_set {enabled,
   reason}` (UI/API/MCP через `/commands`), свёрнутое в `RunState.upstream_auto_paused`: ни автора,
   ни авто-проверок, ни авто-продвижений; поставленные оператором операции обслуживаются.
   `Settings.upstream_advances_per_hour` (2; 0 — без лимита): продвижение сверх лимита ждёт,
   диагностика `lane_held {op, reason}` один раз. `Settings.upstream_author_usd` (2.0; 0 — без
   денежного потолка): расход двух вызовов автора считается по его потоку
   (`thread_committed_usd_exact`) и пишется в `lane_authored.cost_usd`; сумма ≥ потолка — автор
   больше не платит (`lane_held {op: "author", reason: "cost_cap"}`). Всё видно в
   `upstream_live_view`.
3. **Канарейка (G5).** `Settings.upstream_verify ∈ {canary, full}` (по умолчанию `canary`; legacy —
   `full`). Задача с `eval.canary`: эквивалентность — одна пара старая/новая база под env канарейки и
   её таймаутом, допуск `atol + rtol·max|mean|`, воспроизведение метрики источника не требуется
   (другой срез). Без объявленной канарейки — прежние полные повторы. Профиль пересчитывает
   `gate_matches_policy` из настроек и задачи. Отказ от повторов `repair_gate: probes` не меняется.

- **Выход из цикла.** Пауза, остановка или конец прогона больше не бросают операцию в полёте:
  `upstream_serve.py::drain_upstream_job` (после слива оценок в `orchestrator.py`) дожидается
  операции, чей claim уже записан, и записывает её начисления и вердикт (или предложение); ещё не
  заявленная операция отбрасывается без claim — запрос из очереди остаётся в очереди. После
  остановки прогона и под выключателем автоматики новая фаза не начинается; оплаченный черновик
  записывается и предлагается следующим движком из сохранённого тела.
- **Отказ навсегда.** Автоматический шаг, отклонённый полосой по причине самого предложения
  (не из `TRANSIENT_REFUSALS`), записывается один раз (`lane_held`, `reason: refused:<code>`), и
  `auto_next_op` его больше не задаёт — следующие предложения и автор не стоят за ним.
- **База узла.** Сборка от файлов родителя (improve, слияние, пересборка, refine_block абляции,
  инъекция на родителе) привязывает Developer к базе файлов родителя и пишет её в
  `node_created.base_selector`; инъекция с `forked_from` пишет базу исходного узла; цепочка
  Developer включает `repair_developer` фасада.
- **Коммит продвижения** перепроверяет базу и новую работу в очереди (`upstream_work_pending`), а
  нечитаемая база — отказ в квитанции, а не исключение из цикла.
- **Очередь** — объявленный писатель инварианта №1 (`events/types.py::LANE_QUEUE_APPENDABLE`,
  `tests/test_lane_queue_appendable.py`); повтор отклонённого запроса возвращает отказ, а не
  «queued». Режим для читателей — режим, с которым вооружился живой движок (`served_mode`);
  инструкция говорит о выключенной автоматике.
- **Стоимость хода.** Активная база кэшируется по тому, что её двигает; автор помнит источник без
  номинаций по ревизии базы (а починенный — ещё и по файлам ожидающих узлов на его путях); курсор
  очереди считается без полной свёртки; предпроверка черновика вызывает функции самой полосы.
- **Доска.** Продвижения не выпадают из окна истории свёртки; заметка Developer называет только
  продвижения в его базе; отменённый claim проверки оставляет предложение в работе.
