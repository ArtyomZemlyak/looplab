## 1. Проблема на прогоне `minionerec-lora-v1`

Прогон 2026-09-30 12:47 → 2026-10-01 (жив на момент чтения), задача `kind: repo`, редактируемый путь —
рабочая копия тренировочного репозитория MiniOneRec (`editable_path` в `task.snapshot.json`),
`edit_surface: ["**/*"]`, `protect: []`, оценка — `bash MiniOneRec/looplab/run_experiment.sh` с
метрикой `InCart_FilteredUnseenRecall@20` из stdout. Узлы — внедрённые оператором черновики
(`inject_node`, один узел = один `experiment.env`) плюс карточки исследователя.

### 1.1 Как база попадает в узел и что видно, когда она движется

**Код [измерено по дереву].** Материализация узла — три шага в одном порядке:
`engine/workspace.py::WorkspaceSeeder.materialize` вызывает засев (`seed_workspace` →
`engine/workspace_seed.py::seed_candidate_workspace` → `engine/workspace_seed.py::seed_repo_tree`:
`git ls-files -z` по исходному пути и копия КАЖДОГО отслеживаемого файла в его состоянии в рабочем
дереве), затем пишет поверх файлы узла (`write_node_files`), затем ассеты задачи. Засев идёт на
каждом НОВОМ жизненном цикле (`engine/evaluate.py::EvaluateMixin._eval_prepare_workdir`); ремонт
внутри цикла базу не перечитывает — он только дописывает оверлей
(`engine/evaluate.py::EvaluateMixin._eval_apply_repair`, «re-materialize before re-eval» пишет
только файлы узла). Отсюда поправка к формулировке «база заморожена на старте»: база **не
снимается** на старте — она читается вживую из рабочей копии оператора; движок в неё **не пишет
никогда**. Всё, что узел улучшил, живёт только в `Node.files` (оверлей на базу,
`core/models.py::Node`), и пути из узла обратно в базу нет.

Что записывается, когда база движется:

- `run_started.workspace` — отпечаток источника на старте (`WorkspaceSeeder.workspace_fingerprint`:
  для git — один HEAD);
- `workspace_changed {was, now}` — только при ВХОДЕ в прогон (resume), и только при новом
  отпечатке, то есть при новом HEAD: незакоммиченная правка строки не даёт
  (`engine/setup_phase.py::workspace_moved`, doc 69 69.20);
- `metric_provenance.comparability.substrate` на `node_evaluated` — HEAD + дайджест грязного
  состояния, снятый **на терминале узла**, а не на его засеве
  (`engine/evaluate.py::EvaluateMixin._eval_write_terminal` вызывает
  `WorkspaceSeeder.substrate_fingerprint` «LIVE rather than from the folded pin»); это
  дискриминатор, сертифицировать он не может (`engine/comparability.py::comparability_record`).

### 2.1 Почему это не пересмотр doc 37

Doc 37 мерил worktree как РАБОЧИЙ КАТАЛОГ КАЖДОГО УЗЛА: +2.1 % диска, засев — 0.02 % прогона, и
дисквалификатор — worktree выписывает КОММИТ, а засев копирует РАБОЧЕЕ ДЕРЕВО (на тестовом стенде
v1 10 из 17 отслеживаемых файлов были грязными). Здесь предлагается другой объект: один worktree
базового репозитория на один КАНДИДАТ upstream (единицы на прогон, не сотни), где Maintainer
обобщает изменение и откуда идёт коммит. Узлы по-прежнему засеваются копией. Дисквалификатор doc 37
при этом действует и здесь, и предложение обязано его учесть: worktree кандидата нарезается не от
HEAD, а от коммита, снятого с рабочего дерева без его изменения (**[рассуждение]** `git stash create`
даёт такой коммит из индекса и отслеживаемых правок и не трогает ни дерево, ни ссылки), — иначе
Maintainer обобщал бы фикс поверх базы, на которой узел не бежал.

**Поправка ревью.** `git stash create` — лишь возможный источник tracked snapshot:
при чистом дереве он не создаёт коммит; untracked protected files, submodules,
LFS payloads, data/references и task assets им не архивируются. Недостижимый объект
может удалить GC. Для 72.1 нужен сохранённый, достижимый run-owned snapshot и явная
граница его покрытия. Снимок обязан соответствовать фактическому засеву; одно
наблюдение HEAD/dirty до или после копии не доказывает атомарность дерева.

## 3. Предложение: «полоса upstream»

Цель — чтобы находка узла, которая принадлежит пайплайну, становилась частью базы один раз, с
доказательством, что ничего не сломано, и с записью, по которой видно, какой узел на какой базе
бежал. Наука узла (рецепт) остаётся в узле.

### 3.1 Классификация диффа узла: РЕЦЕПТ против ВОЗМОЖНОСТИ

- **РЕЦЕПТ** — ручки эксперимента и конфиги, которые и есть гипотеза: остаётся в узле.
- **ВОЗМОЖНОСТЬ** — код: новый режим, фикс пайплайна, подготовка данных, сценарий стадии.

Строится на том, что уже есть: `engine/activation.py::node_change` (что узел изменил — его линия
против БАЗЫ, после `65551da0`) и `engine/activation.py::is_config_path`. Но раздел 1.2 показывает,
что класс файла недостаточен: три фикса пайплайна — строки `experiment.env`. Поэтому классификация —
по СТРОКЕ/ханку, а не по узлу, и по трём осям:

1. путь (`is_config_path`);
2. происхождение ханка — идея (`node_created`) или ремонт (`node_repaired` с `reason` из
   `core/models.py::FAILURE_REASONS` и `triage_action`); ремонт с инфраструктурной причиной
   (`crash`, `oom`, `setup`, `timeout` на стадии подготовки) — кандидат в возможность, даже если он
   живёт в конфиге (тогда upstream — это ДЕФОЛТ в раннере, как сделал оператор);
3. дубликат базы — ханк, который воспроизводит уже существующую возможность (узел 19), — сигнал не к
   upstream, а к тому, что рецепт можно было выразить без него.

Итог — один класс на ханк, записанный рядом с `activation.change_class`, а не новый смысл старого
поля: `change_class` гейтит вердикт активации, и менять его значение нельзя.

Классификация **номинирует**, но не разрешает публикацию. `reason_findings`, crash
или env-строка не доказывают инфраструктурность и не дают прав на защищённую
поверхность. Source lineage/attempt, хэш исходного diff и подтверждение оператора
должны сохраняться; изменившийся source делает nomination устаревшей.

### 3.2 Кандидаты и порядок

1. Фиксы ремонта инфраструктурных отказов — дёшевы и повторяются (раздел 1.2). Источник —
   `RunState.repair_ledger`, но с порогом не «≥ 2 узла уже заплатили», а «≥ 1 ремонт + триггер
   присутствует у ещё не запущенных узлов» (проверяемо: триггер — условие из `reason_findings`
   ремонта; **[рассуждение]** для env-триггеров это статическая проверка их `experiment.env`).
2. Возможности оценённых узлов, чемпион первым: его код уже прошёл измерение.

### 3.3 Роль Maintainer

Отдельная роль (не Developer: у неё другой предмет — база, а не узел) в worktree базового репозитория,
по одному на кандидата, нарезанном от коммита рабочего дерева (2.1). Обязанности:

- новое поведение — за флагом, по умолчанию — старое (у оператора это уже так: `SFT_DATASET_NUM_PROC`
  по умолчанию 1 только под `SFT_TRAIN_DATA_ROOT`, `${VAR:-…}` уступает значению узла);
- убрать хардкоды узла (`BACKBONE=qwen35_0.8B` единственный в `train_q2replay.sh`, пути `/var/tmp/…`);
- тесты репозитория, если они есть; если нет — шаг гейта 3.4 их заменяет;
- задокументировать ручку там, где их ищут Developer и исследователь (в MiniOneRec — рядом с
  разделом про ручки, который цитирует цель прогона).

### 3.4 Гейт

- **Тесты репозитория** и **критик** (форма уже есть: `repair_critic_verdict`).
- **ЭКВИВАЛЕНТНОСТЬ.** Рецепт узла-источника на новой базе воспроизводит его метрику в пределах шума.
  Для возможности чемпиона — полная переоценка с полом шума (`engine/noise_floor.py::NoiseFloorMixin`).
  Для фикса ремонта канарейки **недостаточно**. **[измерено по `run_experiment.sh` из засева]**
  Канарейка (`LOOPLAB_CANARY=1`) ставит `SAMPLE=2000` и `SFT_EVAL_SAMPLE=200` и не включает
  resume-сейв. **[рассуждение]** Тем самым она убирает триггеры всех трёх падений: потоковый
  источник `SAMPLE=-1` (падение 1), valid-сплит меньше выборки (падение 2), часовой сейв (падение 3).
  Нужен прогон стадии, на которой случился отказ, с её настоящим триггером: падения 1 и 2 наступили
  на подготовке данных, за 152 и 281 с оценки. Канарейка остаётся проверкой того, что уменьшенный
  путь не сломан. **Пример трудности [измерено]:** один и тот же рецепт узла 2 дал
  0.1126388 на исходном `run_experiment.sh` и 0.1114069 на бэкпортированном (Δ = −0.0012, одна пара);
  **[рассуждение]** одна пара не отличает дрейф базы от недетерминизма GPU-обучения, поэтому
  эквивалентность — это сравнение с полом шума, а не с одним числом.
- **РЕГРЕССИЯ.** Флаг выключен → старые рецепты исполняются байт-в-байт как раньше. **[рассуждение]**
  Дешёвый зонд в этой задаче уже есть: ключ кэша подготовленного датасета кодирует параметры
  (триаж узла 2 цитирует его как `n-1 … e20000`), так что совпадение ключа у старого рецепта на
  старой и новой базе — проверка без GPU.
  Поправка ревью: совпадение cache key проверяет только этот ключ, не содержимое
  кэша, поведение тренера или оценку. «Байт-в-байт» заменяется проверяемыми
  observable invariants старого рецепта: входы/выходы стадии, defaults, аргументы,
  артефакты и tests. Это ограниченное evidence, не доказательство всех регрессий.
- **КОНТРАКТ ОЦЕНКИ НЕ МЕНЯЕТСЯ НИКОГДА** этим путём. Квитанция `seed_from_run`
  (`engine/eval_contract.py::EvalContract`: ридер, команда, объявленные пути) — нужна, но не
  достаточна: она декларативна и байтов скорера не видит. В этой задаче команда оценки —
  `run_experiment.sh`, который и тренирует, и оценивает, а `protect: []`, так что квитанция ответит
  `same` на правку того самого файла, что считает метрику. Требование гейта: ни один ханк кандидата
  не касается пути оценки; для совмещённого скрипта это требует от оператора объявить защищённый
  регион или вынести оценку в свою стадию — решение оператора, не Maintainer'а.
  Поправка ревью: неизменный entrypoint не защищает импортируемые evaluator
  dependencies, labels, split/filter и metric reader. Gate требует operator-owned
  границы оценивания и её byte evidence; protected regions сегодня не являются
  готовым API. Если trainer/scorer совмещены и границу нельзя проверить, продвижение
  отказывается. Declared same и noise floor эту неизвестность не закрывают.

### 3.5 Слияние

В собственную ветку прогона — автоматически после гейта. В общий (командный) репозиторий — только
PR/MR для человека; движок туда не пушит.

Автоматическое слияние — будущий отдельный opt-in оператора, а не следствие
`repair_candidates` или model verdict. До него — явное подтверждение конкретного
кандидата и compare-and-swap на ожидаемую базу. Owner checkout не переписывается;
параллельное изменение базы требует нового решения, не silent rebase.

### 3.6 Продвижение базы внутри живого прогона

- Журналируемое событие `base_advanced {commit, parent_commit, source: {node_id, attempt, hunks},
  evaluation_contract_digest, scorer_digest}` — единственный способ, которым база движется внутри
  прогона, включая ручной бэкпорт оператора (сегодня он не записывается ничем, раздел 1.1).
- База ПРИКОЛАЧИВАЕТСЯ к коммиту: засев читает дерево коммита, а не живую рабочую копию. Это
  делает переигровку детерминированной и закрывает тот же пробел, что открытый пункт doc 67
  `repo-base-tree-not-archived` (база записана дайджестом, не содержимым).
  Уточнение: детерминированный event replay уже восстанавливает state. Повторное
  выполнение требует доступных archived bytes, data/reference identities,
  evaluation boundary и environment; commit/digest по отдельности этого не дают.
- Ещё не запущенные узлы засеваются на новой базе; уже идущие доигрывают на своей.
- Каждый узел записывает базу, на которой его ЗАСЕЯЛИ (`workspace_seeded`), а не ту, что была на
  его терминале (раздел 1.1), — чтобы сравнения можно было фильтровать по базе.
- Оверлей, который не накладывается на новую базу (трёхсторонний merge: старая база, новая база,
  оверлей), оставляет узел на старой базе с пометкой. Оверлей, копирующий файл целиком (узел 2,
  раздел 1.4), — частый случай такого конфликта, и его надо отличать от настоящей правки.

### 3.7 Пакеты работ

- **WP1** — upstream фиксов ремонта + `base_advanced` для не запущенных узлов + база на засеве в
  записи узла. Без Maintainer'а: фикс ремонта переносится как дефолт за флагом, кандидата подтверждает
  оператор (как сегодня), но движок делает это записанным и проверенным.
- **WP2** — Maintainer: обобщение возможностей (сценарии стадий, режимы, подготовка данных),
  классификация ханков 3.1, гейт эквивалентности.
- **WP3** — UI/отчёт: на какой базе бежал узел, какая возможность пришла из какого узла.

## 4. Риски и открытые вопросы

1. **Сравнимость при дрейфе базы.** Продвижение базы делает узлы по разные его стороны
   несравнимыми, если гейт эквивалентности не доказал обратного; `comparability` уже отказывает
   по `substrate` (`engine/comparability.py`), так что каждое продвижение режет таблицу прогона.
   Вопрос — когда эквивалентность разрешает считать узлы сравнимыми, а когда нет.
2. **Качество обобщения Maintainer'а.** Тот же Developer-класс ошибок (узел 19 не увидел
   существующую возможность); гейт ловит поломку, но не плохую абстракцию.
3. **Цена эквивалентности на GPU.** Полная переоценка чемпиона здесь — ~6.9 ч на одной L40S; пол
   шума требует нескольких. Для фиксов ремонта — минуты (стадия отказа), для возможностей — часы.
4. **Конфликты с параллельными оверлеями.** См. 3.6; целиком скопированные файлы — главный
   источник.
5. **`merge_mode` и дедупликация карточек/новизны.** Возможность, уже поднятая в базу, не должна
   предлагаться заново, а слияние двух узлов, один из которых несёт уже поднятый ханк, не должно
   его дублировать. Нужна запись «этот ханк теперь в базе» для проверок новизны.
6. **Доверие и безопасность.** Код узла исполнялся в песочнице оценки; в базе он исполняется в
   каждом следующем узле и, через PR, у людей. Поднимать можно только то, что прошло патч-гейт
   поверхности и `protect`, — а здесь `protect: []`, так что защищать нечего, пока оператор не
   объявит путь оценки (3.4).
7. **Детерминизм переигровки.** Пока база читается вживую (1.1), переигровка прогона на другом
   состоянии рабочей копии исполняет другой код; приколачивание к коммиту (3.6) — предпосылка
   всего остального.

## 7. Контракт первого шага после ревью

72.2 фиксирует effective editable bytes **в destination после seed/protected и до
data/reference mounts, node overlay и task assets**. Все расширения файлов,
включая `experiment.env`, входят в scope. Изменение источника во время копии
может дать смешанное дерево: receipt описывает полученную копию, не утверждает,
что существовал один соответствующий исходный commit.

Receipt должен иметь version, scope, complete/digest и причину unknown. Непрочитанный,
нестабильный, неподдерживаемый или превышающий bounded budget seed не получает
digest частичного дерева. Это diagnostic, не новый evaluation gate. Новый seed
при reset записывается отдельно; ремонт в текущем workdir не снимает новую базу.
Успешный terminal сохраняет тот же receipt в metric provenance с lifecycle;
прочитать source repo на terminal для этого нельзя. Старые записи не дополняются
предположением о базе. Прежний live `substrate` остаётся отдельным историческим
дискриминатором; receipt не сертифицирует сравнимость, equivalence или archive.

Приёмка: tracked dirty tree и удаление файла; env без source suffix; non-git/all;
несколько editables и untracked protect; mount и overlay не меняют receipt; source
drift после seed; reset/repair; unreadable/unstable/over-budget → unknown. Короткий
protected training probe должен связать receipt засева с настоящим terminal,
изменить source после seed и показать отсутствие повторного обучения.

## 8. Первый шаг (коммит `1ef15258c`) и границы его проверки

Ревью и правки плана сохранены отдельно в `07530afd0`, до реализации.
`workspace_seed.seeded_base_revision` полностью хеширует regular files полученного
дерева: относительный путь, executable bits и SHA-256 содержимого. Все суффиксы
включены; untracked protected файлы и несколько editables тоже. Ограничения:
20 000 entries и 64 MiB суммарных данных. Непрочитанное, изменившееся при чтении,
неподдерживаемое или превышающее лимит дерево возвращает `complete:false`,
`digest:null` и reason; частичный счётчик — диагностический, не идентичность.
На публичном API счётчик называется `file_count`, чтобы не попадать под очистку
поля с исходниками `files`. Содержимое файлов в receipt не записывается.

Engine включает capture при засеве; Developer commands сохраняют прежний путь
без дополнительного хеширования. Receipt хранится в `EvalAttempt`, не в общем
кеше: новый reset/materialize получает новую запись, repair overlay её не заменяет.
Успешный primary terminal переносит receipt, не перечитывая source для этого поля;
replay восстанавливает его через существующий metric provenance. У failed узла
seed остаётся в timeline. Legacy, заменённый seam без receipt и recovery уже
завершённой оценки без сохранённого seed receipt остаются неизвестными. Confirmation
workspaces имеют seed diagnostic; эта реализация не добавляет им отдельного
score-bound receipt. Ни одного нового gate, ожидания или разрешения на upstream нет.

**Проверки.** `tests/test_seeded_base_revision.py` покрывает контракт §7, включая
middle-byte mutation большого файла и отказ от частичного digest. Native symlink
проверка пропускается только при Windows error 1314 (нет права создать symlink).
Команда `benchmarks.external_idle_recovery_smoke --case all --seed-base-recovery`
проверена на двух приватных прогонах: потеря MCP агента и остановка/явный resume
движка. В каждом два настоящих protected SGD score execution, метрики

## 9. Ревью следующего шага: архив полученной базы

Первый prerequisite 72.1/67.12 — сохранить байты того же destination seed,
который уже назван digest. Повторная копия source или HEAD archive после seed
может дать другую базу. Поэтому запись архива должна получать **те же прочитанные
байты**, из которых 72.2 считает digest, до mounts/overlay/assets.

Решение: отдельный run-owned `base_snapshots/<digest>/`, приватная временная
директория и публикация целиком через durable no-replace rename. Одинаковая база
переиспользуется только после bounded проверки содержимого и executable bits.
Повреждённый существующий архив не заменяется молча. Partial/unknown seed не
публикуется. Receipt отдельно различает известную идентичность и доступность
архива: ошибка записи/публикации не отменяет измеренную оценку и не даёт новых
разрешений. Обрыв до публикации может оставить orphan staging; он не считается
архивом. Ограничения 72.2 остаются; пустые директории и полные POSIX permissions
не входят в идентичность regular-file contents.

Перед использованием архив нужно проверить относительно receipt, а не доверять
имени каталога. Приёмка: база после удаления source и node workdir; dirty/env/
untracked protect; исключение overlay/mount; одинаковая база без дубликатов;
конкурентная публикация; недоступный/повреждённый архив и unknown seed без
ложного успеха; отсутствие нового evaluation wait. Живой SGD/MCP probe должен
проверить прежнюю и новую архивированные базы после drift/reconnect.

Этот шаг пока не закрывает 72.1: scorer dependency boundary, перенос архивов
в export bundle, выбор pinned base и gate/CAS advancement требуют следующих
изменений. Event replay уже существует; повторное исполнение требует ещё
data/reference/environment identities и защищённого evaluation boundary.

## 10. Архив засева: реализация prerequisite 72.1

`engine/seed_archive.py` сохраняет regular files под `base_snapshots/<digest>/`
в run directory, до overlay/mount/assets. Запись получает bytes из прохода 72.2,
а не копирует source заново. Содержимое staging проверяется тем же bounded digest;
файлы и directory entries синхронизируются перед durable no-replace publication.
Существующий архив принимается только при совпадении содержимого; конфликт не
перезаписывается. Параллельные одинаковые seed используют один архив.

`base_revision.archive` имеет version, status (`stored` / `unavailable`), reason
и только run-relative path. Unknown seed, ошибка чтения/записи/sync/rename или
повреждение существующего архива не дают `stored`; известный seed digest и
материализация остаются доступны. Ошибка файла не публикует частичный архив.
При обрыве до публикации staging может остаться; `.pending-*` не является
подтверждённым архивом и не выбирается для выполнения. Права файлов приватные,
executable bits сохраняются. POSIX permissions, пустые директории, mounts и
environment не входят в эту идентичность. На filesystem без durable no-replace
архив объявляется недоступным; replacing fallback не применяется.

`verified_seed_archive(run_dir, receipt)` проверяет format/path и все содержимое
перед выдачей пути. Directory name сам по себе не доказательство; escape, reparse,
missing/corrupt archive возвращают unavailable. Это библиотечный reader основы
upstream; отдельной команды restore/execute и переключения базы пока нет.
`stored` — результат публикации в момент capture, не live health. Event replay
сохраняет receipt, но не восстанавливает отсутствующий архив; перед использованием
нужна новая проверка bytes.

Ревью сохранено до реализации в `1f46c508f`. Приёмка: 66 passed / 4 skipped
в archive/seed/Developer/multi/protected наборе; 844 passed / 3 skipped при
проверке package aliases и materialization seams; 85 passed в evaluation/replay
наборе; 50 passed в API/events/diagram/docs contracts. После финального ревью:
68 passed / 1 skipped в archive/layering/containment/docs наборе. Пропуски —
явные platform/privilege ограничения; POSIX executable/umask case на этой
Windows машине не исполнен. `mkdocs build --strict` прошёл.

Native Windows проверка выявила `fsync` на read-only descriptor; он заменён
write-capable дескриптором. Root archive directory публикуется отдельным
durable rename; вложенные parents — canonical strict writer. Ошибки sync/rename
сохраняют `unavailable`, не фиктивное подтверждение.

Живой `--case all --seed-base-recovery` повторён на финальном коде в
`.tmp/doc72archive-verified-proof/acceptance.json`: агент потерян/подключён заново
и движок остановлен/явно resumed. В каждом два protected SGD execution, без
повторного обучения от reconnect. Старый/новый seed archives проверены из
public MCP receipt, включая `experiment.env` и неизменный scorer; generation
и sequence совпадают, `inspect`/`replay` проходят. Отдельный тест удаляет source
и node workdir, затем читает архив и выполняет сохранённый простой scorer.
Это не повтор полной удалённой ML-задачи и не доказательство model judgment.

72.1 остаётся открытым:
Archive export реализован в §12; следующий шаг — operator-owned scorer boundary, затем pinned
base selection, gate/CAS advancement. 67.12 частично реализован, universal replay

## 11. Ревью export-bundle перед реализацией

Экспорт должен переносить только base receipts из `workspace_seeded` и
`node_evaluated.metric_provenance`, включая историю вытесненных generations.
Не сканировать все каталоги архивов: unreferenced и staging не являются evidence.
Одинаковые базы копировать один раз, а ссылки на события сохранять отдельно.
Raw events не переписывать. Legacy без receipt сохраняет прежний формат bundle.

`base_snapshots/index.json` связывает исходный receipt/event sequence с результатом
экспорта (`exported` / `unavailable` + reason), который не заменяет исторический
`archive.status`. Missing, corrupt, unknown или неподдерживаемая база не получает
подтверждение. Не подставлять нынешний source repo. Проверить копируемые bytes
относительно ожидаемого receipt **до публикации**: предварительная проверка source
не закрывает drift между проверкой и копированием.

RO-Crate перечисляет каждый перенесённый файл и index с SHA-256. Verification
также связывает index с скопированным event log и проверяет whole-base digest и
executable bits; per-file bytes checksum один не обнаруживает потерю режима.
CLI отдельно называет количество перенесённых и недоступных receipts. Correct
package с явными omissions не означает полностью воспроизводимую ML-задачу.

Output внутри исходных base archives или поверх run directory должен быть
отклонён до записи; linked archive output не должен вести запись наружу.
Приёмка: export после удаления source/workdirs; два base digest и reset history;
дедупликация; unavailable/corrupt receipts; source drift при копии; tamper/missing
файлы и mode; опасные output/reference paths; legacy compatibility. Живой SGD
probe переносит обе базы, проверяет crate и исполняет сохранённый scorer отдельно
как export validation (это не новая измеренная оценка узла).

72.1 остаётся открытым: следующим будет operator-owned scorer boundary, затем
pinned base selection и gate/CAS advancement. Data/environment не включаются.

## 12. Export-bundle: реализация prerequisite 72.1

`engine/bundle_bases.py` собирает receipts из всех записанных seed/terminal events,
сохраняя event sequence, node/generation и исходный receipt. `index.json` имеет
version 1 и отдельный export outcome; его бюджет проверки — 32 MiB. Valid identical
identities копируются один раз. Unknown/missing/corrupt архивы отмечаются unavailable;
live repo не используется. `copy_seed_archive` проверяет actual read bytes против
ожидаемого receipt до публикации, сохраняя executable bits. RO-Crate перечисляет
index и все перенесённые файлы. Legacy bundle без receipts остаётся прежним.

`verify_bundle` связывает index с неизменённым event log, проверяет членство файлов
в crate и whole-base identity, а не только byte checksums. Неизвестные receipts
не становятся исполненными узлами или архивами. CLI показывает число distinct
archives, exported/unavailable receipts. Source run/archives нельзя выбрать как
output, linked archive root не используется для записи. Не добавлено новой оценки
узла, публикации метрики или engine wait.
