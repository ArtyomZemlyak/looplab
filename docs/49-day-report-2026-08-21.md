# The record stopped lying, and the watchdog's diagnosis finally reached the agent that repairs

*2026-08-21. Written for the operator. Every number here was measured on this box; where a claim was
made and later corrected, the correction is in the text rather than in a footnote.*

## 1. Two agents watched one run for ten hours and reached opposite conclusions

`runs/e5small-dr-unified-v4` node 3 drew **21 `train_monitor_alert` rows** over ten hours. Fifteen
named a mechanism and converged on it precisely: the DCL mask sentinel is a FINITE `-1e9`, so a row
whose mask removes every negative drags the batch mean by roughly `-1e9/batch` and the contrastive
objective — bounded below by 0 as written — becomes unbounded below. The measured trajectory on
those rows never wavered: `direction=descending`, `first=40.07`, `last=-2.4e7`.

The stage then hit its ceiling. The repair judge was handed the stderr tail, the code tail and the
repair history — **and not one word of any of that** — and opened: *"Healthy training run … a pure
speed failure, not a correctness one."* It cut `n_epochs` 15 → 3, left `dcl_threshold` and the
sentinel untouched, and the next attempt re-ran the same degenerate objective. **~17 GPU-hours.**

Nothing new is measured to fix this. The rows were already durable, already keyed to the node,
already paid for. The change is a READ: the verdicts are spliced into the repair prompt under a
heading that says **whose opinion it is**, each row carries its own confidence, and the series is
**not collapsed** — on this node the watchdog said `healthy` at 0.85 five times, twice directly
between two `broken` verdicts at the same confidence, and that it had no settled answer is
information the Developer should have rather than something an average hides. The `trajectory` rides
alongside on its own `measured:` line because it is the one field on those rows that is not a
judgement: the verdicts contradicted each other five times and the trajectories never did.

## 2. Why nothing stopped it — and why that is not a bug to fix

**Zero of node 3's 24 alerts carry `stop_decided` or `kill`.** Not "the bar was too high": five
`broken` verdicts sat at or above the 0.8 bar (0.85, 0.80, 0.85, 0.85, **0.90**), all attributing
the fault to the implementation. Each was blocked, and by two different rules:

| alert | confidence | streak before | direction | blocked by |
|---|---|---|---|---|
| #5 | 0.85 | 0 | descending | streak < 2 **and** the trajectory veto |
| #8 | 0.80 | 1 | descending | streak < 2 **and** the trajectory veto |
| #11 | 0.85 | 0 | descending | streak < 2 **and** the trajectory veto |
| #16 | 0.85 | 0 | unknown | the streak alone |
| #18 | **0.90** | 2 | descending | **the trajectory veto alone** |

`trajectory_vetoes_kill` refuses to end a descending, non-anomalous curve. For a loss bounded below
that is right. Node 3's objective is unbounded below, so **descent is the symptom**. The explosion
rung that should have caught it reads `abs(window.maximum)` — the SIGNED max, i.e. the value nearest
zero for an all-negative loss — so it structurally cannot fire on a run diverging downward.

This is already a permanently declined item, with the arithmetic:
the `explosion-rung-cannot-be-magnitude-symmetric` refusal (its marker lives in `engine/train_monitor.py`, beside the code it refuses, and is not re-spelled here: a slug names exactly ONE item). 28 of the 249 stage logs on this box reach
|loss| ≥ 1e8 and 26 of them produced a metric, 16 above 0.87. Any bar that catches the broken node
n74 (peak 2.54e+08) kills champion n48 (2.53e+08, metric 0.8835) — 5.64x versus 5.65x, and the
champion is higher. So the monitor is **structurally barred** from stopping this class of run, which
is exactly why getting its diagnosis to the repairer is the answer rather than a consolation.

**And the streak is defeated by a wobbling judge.** Node 3 drew 13 `broken` verdicts in 24 and never
two in a row at ≥0.8, because `healthy` verdicts at 0.85 interleave. The gate asks for CONSECUTIVE
agreement from a judge that is measurably not consistent.

A windowed rule — "at least 2 of the last 6 are broken + implementation + ≥0.8" — fires on **exactly
one node in 213 alerts across 30 nodes**: this one. It fires on **zero** nodes that produced a
healthy metric, including all four champions and `e5small-dr-unified-v2` node 2, which drew 33
alerts and scored 0.0. That is a JUDGE-shaped rung rather than a trajectory-shaped one, so the
declined item — whose corpus has **zero** watchdog rows — does not cover it. **It is not shipped:
n=1.** Perfect separation over 30 nodes with one positive case is evidence the rule does not fire
wrongly on 29 known cases, not evidence that it generalises. And the windowed change alone would be
inert, because the veto was #18's only remaining blocker.

## 3. The records that lied have been repaired

`Idea.params` is a PROPOSAL. Under `params_style: "none"` the engine applies nothing — the Developer
realises the idea by EDITING THE REPO — so a deviation is legitimate. What was not legitimate is
that the record kept only the proposal while every reader presented it as what produced the metric.

`looplab backfill-applied-params <run_root> --apply` went back and read the workdirs that survive.
**23 events written; a second run wrote 0.** Of 23 nodes with a metric and no record: **21
recovered, 2 not** (both declare no numeric coordinate at all), **6 diverge** from the proposal and
**6 have carriers that disagree with each other**.

* The v2 champion at **0.793426** is recorded 8192 / 2 / 15 and **ran 512 / 32 / 3**.
* The v8 champion at **0.762048** comes back as a **CONFLICT**: the config document says 8192 while
  the training script assigns 4096 — R-Drop's second forward pass will not fit at 8192 even on a
  140 GB H200, so the Developer halved the batch and deliberately left the document alone to keep
  the completed `mine` stage reusable. Both readings are kept, with file and line. Neither is
  declared to be "what the node used", because the record cannot say.

`champion_caveats.applied_params_diverged` already counted both divergences and conflicts; it simply
had nothing to read. It now fires on both champions.

Two properties make a record repair safe, and they are the whole design: **a live record always
wins** (a reconstruction may never overwrite a measurement, which is also the entire idempotence —
the second pass finds what the first wrote and declines), and **absence is recorded as absence** (a
node whose workdir is gone gets a row that says so, because "the workdir is gone" and "the proposal
is what ran" are opposite statements and the second is the one every reader made by default).

## 4. An agent can now ask what actually differs between two nodes

`diff_nodes(left, right, section?)` returns the experiment's own source diff, the parameters
PROPOSED and the parameters that actually RAN as **two separate columns**, and both metrics with the
comparability verdict attached. Read off the folded `RunState`, so the files shown are the ones the
node's LAST attempt ran — v8 node 3 was repaired five times and ended with seven files against the
five it was created with, and its metric belongs to the seven.

The property the tests are built around: **an empty diff and a missing diff never render the same.**

Driving it over the just-repaired record found two more real gaps: it rendered `diverged` and
**silently dropped `conflicts`**, so it printed nothing at all about the v8 champion; and it called
an UNSETTLED coordinate `(absent)`, the same absence-versus-emptiness confusion one level down.

## 5. The record now keeps 16 KB of a failure the classifier read 64 KB of

`res.stderr` was clamped at 64,000 bytes per stream when the classifier read it. 500 characters
survived to disk. **Not one of the 122 stored tails contains a torch-OOM marker** — five are a
launcher's opaque `Root Cause … exitcode: 1` block and two are nothing but a progress bar. The
deleted marker rule replayed over the durable record scores **0 of 23** OOMs and **16 of 23** over a
wider window; the diagnostician goes 82.2% → 86.4% on the same widening.

A SECOND column, not a bigger `error_in`: that one string is also the repair prompt, the judge's
history and the terminal's `error`, and widening it would multiply the paid prompt by 32. The guard
with teeth asserts **nothing on the prompt path reads the wide column**, and its positive half
asserts the judge's history still reads the narrow one, so "nobody reads either" cannot pass.

16 KB and not 64 KB, and the number is about secrets rather than bytes: the redactor fires 0 times
at 500 characters, **36** at 16 KB — catching a real `password` — and 384 at 64 KB.

## 6. The run was restarted, and why that was necessary

The engine launched 2026-08-20 03:22 and **pins its own code**. The dark-GPU fix merged 2026-08-20
18:52, 15.5 hours later, so it could never reach that process — GPU 1 was dark for 14.5 hours while
GPU 0 ran alone, and the event log (not a snapshot) is what says so: no stage has run on a second
node since node 1 finished.

`stop` was not enough. It breaks the engine on its NEXT loop iteration, which would have been ~5.6
hours away behind node 3's training. The process was terminated directly and resumed from its log,
onto master — recovering 27 commits including everything above.

**Measured inside v4, the one comparison genuinely on one scale:** node 0 ran 5 epochs in 4.72 h and
scored 0.758851; node 1 ran 15 epochs in 9.32 h and scored 0.764853. Tripling the epochs bought
**+0.006 for double the wall clock** — and both nodes DECLARE 8192 / 2 / 15 while node 0 actually
ran 4096 with 5 epochs and temperature 0.01.

## 6a. …and then the veto was made to yield to a citation

§2 above says the monitor is structurally barred from stopping this class of run and that getting
its diagnosis to the repairer is therefore the answer. That was half of it. The other half is that
**the judge had already done the work and could not make it count.**

`_LOOK_INVITATION` has told the watchdog since 2026-08-18 to read the source before attributing
fault. It did: five of node 3's sixteen `broken` verdicts cite a file and line in their prose,
including the line that declares the finite `-1e9` masked-logit sentinel. The citation lived in
`reason`, which is prose, so nothing re-resolved it — and the engine, unable to tell a verdict that
had opened the file from one that had invented the line number, believed the measurement. Given what
it knew, that was correct.

So the citation is a FIELD now (`evidence_source` / `evidence_locator`), the prompt carries a
checklist saying what earns it, and `failure_diagnosis.evidence_citation_resolves` — which already
did exactly this for the diagnostician — RE-OPENS the place before the gate reads it, confined to
the workdir and refusing `..`, an absolute path and a symlink out. **A citation the engine itself
re-read is an out-of-band fact the model did not author.** Text may nominate; it may never decide.

It lifts the veto and **nothing else** — the confidence bar, the repeated-verdict requirement and
the status all still hold — and only on the REPAIR path. `should_monitor_kill` takes no such
parameter and cannot be handed one, asserted structurally, because the asymmetry is the whole
justification: a kill discards a multi-hour training with no repair, no retry and no refunded slot;
a repair-stop costs one restart of a run the judge has just said is wasted, with the diagnosis
attached.

This is not the rung this repo refuses permanently. That refusal prices a THRESHOLD on the
trajectory and shows no bar separates the broken n74 from champion n48; this is not a threshold, and
n48's run holds **zero** watchdog rows, so it cannot enter this path in either direction.

## 6b. "The check itself was wrong" became something the diagnostician can say

Of the 22 `check_failed` rows on the durable bench, 14 become `not_learning` — the win the ownership
split was built for — and **five were answered back as `check_failed`**, which reads like the
diagnostician restating the status it was handed. Their rationales say otherwise:
*"The check_failed verdict is a false positive: the run actually reached val recall@100=0.8114 …
yet the verifier flagged"*. Two more refute the checker with validation recall taken from **the same
log the checker read**. It was right and had nowhere to put it.

`check_false_positive` is answer-only for the same structural reason `oom` is: the stage check IS
another model's reading of stdout, so "that reading was wrong" is a claim only a second reader can
make. It **admits no metric** — absent from `NEVER_SALVAGED_REASONS`, the neutral position
`not_learning` holds — so a model saying the check was wrong does not thereby score the node. What
it moves is the DIRECTIVE, which now points the repair at the check instead of asking a Developer to
rewrite an experiment whose numbers it has just been told are correct. **The cheapest way to satisfy
a wrong check is to break the thing it was checking.**

## 6c. Where a stop would be worth acting on, measured

Across 237 alerts in six runs, 100 are `broken` and 91 carry a progress fraction. **16 of those 91
(17.6%) arrive at or past 80% of the stage** — clustered on `e5small-dr-unified-v2` node 2, which
scored 0.0. The distribution is roughly bimodal: 12 in the first decile, 17 in each of the 30-40%
and 40-50% deciles, 12 in the last.

The asymmetry is real — a repair-stop DISCARDS the attempt, so stopping at 90% costs a full re-run
to save 10% while finishing costs 10% more and yields a measurement. **It was not shipped.** The
deterministic gate has never fired once in the entire recorded history (zero of 237 alerts carry
`stop_decided`), so a new conjunct would be arithmetic added to a mechanism with no measured
behaviour to correct — and the judge, unlike the gate, is already told its position in every prompt.

## 6d. The chain closed, once, end to end — watched at every link

Everything above is machinery. This is what it did, on `runs/e5small-dr-unified-v4` node 3, hours
after the last of it merged.

**The watchdog cited and the engine went and looked.** Four `broken` verdicts in a row, every one
carrying `evidence_source: code` and a locator the engine RE-OPENED inside the node's workdir:

| # | conf | locator | resolved | acted | streak before |
|---|---|---|---|---|---|
| 1 | 0.85 | `loss.py:497-516` | true | no | 0 |
| 2 | 0.70 | `loss.py:513-516` | true | no | 1 |
| 3 | 0.65 | `loss.py:517-520` | true | no | 2 |
| 4 | 0.85 | `train.log:280-288` | true | **YES** | 3 |

Twenty lines narrowed to four, and on the last tick it stopped citing the SOURCE and cited the LOG —
it went and checked its reading of the code against what that code had printed. The previous attempt
on this same node produced **24 alerts and zero decisions**, five of them confident and all five
blocked by the trajectory veto. Here the veto yielded to a re-read citation and the gate fired for
the first time in the run's history.

**The repair read the diagnosis and did not take it on faith.** The stage ended at 3,069 s against
the previous attempt's 36,005 s, and `node_repaired` carries `reason: not_learning` where the last
one carried `timeout`:

> *"The watchdog's diagnosis is correct and I reproduced the mechanism in code: the ported loss
> removes the positive logit from the denominator while masking negatives at -1e9, so aggressive DCL
> masking (dcl_threshold=0.05) empties the denominator and the loss diverges to -2e10."*

`changed: ['vectorsearch/training/loss.py']` — the file with the bug, not the schedule. `verified`,
`unmet: []`: the engine found in the diff exactly what the repair promised. The previous repair on
this node wrote *"Healthy training run … a pure speed failure, not a correctness one"*, cut
`n_epochs` 15 → 3, and was stamped `unmet`.

**And the objective has a floor again.** Measured on the current attempt's segment of the log alone:

    41 records   first 38.57   last 23.73   min 23.73   epoch 0.58   step 416/2109

The minimum IS the last value — the loss has not gone below its own descent once. The previous
attempt read 38.57 → -2.29e6 within fifty steps and kept falling.

**What this is not.** One node, one chain, no metric yet. Every link was observed, which is more than
"it works"; it is not yet evidence that it repeats. The stage also closed on a TIMEOUT, and the
watchdog's contribution is not separated from the earlier epochs cut — the decision is a fact in the
log, sole causation of the stop is not.

**And the same day's last gap was found by the same run.** Minutes after the repair wrote the above,
`repair_critic_verdict` on the same node wrote *"a pure speed timeout with a healthy training run"* —
verbatim the framing that cost the GPU-hours — because the critic reads the engine's cause column
(`crash`, `crash`, `oom`, `expect_failed`, `timeout`) and I had filed it out of scope that morning.
It decides whether the chain lives. It now reads the same verdicts.

## 7a. A second objective can now be recorded, and it had to be oriented FIRST

The multi-objective machinery is complete end to end — an `eval.metrics` declaration channel, a
writer with `declared`/`auto` provenance, and a non-dominated front in the browser — and empty
exactly in the middle. Measured over every `*.jsonl` under `runs/` (131 files, 15 run directories):
the `declared` channel has produced **zero** values in the corpus's history, and all 1,600 `auto`
values are the engine's own CUDA-probe telemetry in the `specgate*` toys. All 8 evaluated nodes of
the two real task families record `extra_metrics == {}`.

Not a bug, an unused door: `auto` capture fires only for `metric.kind == "stdout_json"` and these
tasks read by `stdout_regex`, so it is structurally off and `declared` is the only way in.

**The order of the fix is the interesting part.** `paretoFront` read every extra key as cost-like —
documented, and harmless only because a constant dimension cannot change a domination. The
objectives waiting to be recorded are QUALITY metrics: a score stage prints ~35 higher-is-better
numbers. Declaring them before the front could orient them would have inverted the ordering
**silently** — every number on screen real, the order backwards. So direction now travels with the
values, and an axis nobody oriented is dropped from the ORDERING while staying visible everywhere
else. Behaviour-preserving today: the seven existing front tests pass untouched.

Then recovery: `backfill-score-metrics` reads the preserved score logs — **28 of 29 scored nodes,
979 values** the record had computed and thrown away. It writes no direction, deliberately; nobody
declared one when those evals ran, and a reconstruction may not assert more than the record
supports. Known limit, recorded per key: the suite prints 2 decimals while the primary is read at 6,
so v4 nodes 0 and 1 — 0.006 apart on recall@100 — are identical on every recovered metric.

## 7b. Why the GPUs idle: §8's first bullet, root-caused

That bullet said five cards sat proposed while a GPU stayed idle, and asked for a time series. The
series arrived, and so did the mechanism.

`_handle_create_actions` is awaited on the main task, but everything under it is **synchronous**:
`_stage_card_creates` → `_prepare_node_idea` → `foresight.propose` → `agent.run_phase` →
`drive_tool_loop` → `llm.chat` → `_bounded_create` → `threading.join`. A `py-spy` dump of the live
engine, sampled twice eight minutes apart, puts asyncio's own `_run_once` **below** that join with no
coroutine frame in between. An entire propose phase — call, parse, call, parse, no `await` anywhere —
is ONE event-loop callback.

That reconciles two observations that first looked contradictory: **243 provider calls COMPLETED**
between 21:26 and 21:45, so nothing was wedged; and node 4's terminal never landed, so nothing else
ran. Both are true because all 243 were inside one callback.

The bill, one evening: node 4's train stage OOM'd and its process **exited at 21:03:40**. Sixty-two
minutes later there was no `stage_finished`, no terminal and no repair — `pgrep -P` showed no
children and all three anyio worker threads sat idle on empty queues. Both H200s idle ~59 minutes.
Propose phases in this run take a **median 10.8 min (n=12, max 38.9)** and one node ran six back to
back: **10 cards added against 5 ever requested for build.** The board filled while the machine that
consumes it never got a turn.

`orchestrator.py:1902` already documents the neighbouring half — production "was gated on occupancy
ZERO, which is exactly backwards." That fixed WHEN a create becomes reachable. This is the other
half: once reachable, it holds the loop for as long as it takes.

Filed with a stack and a number and **no marker**, on the rule that refused one for §0.1 item 9 —
a pin on the synchronous call site survives an offload landing inside `_stage_card_creates`, and a
pin on `to_thread` names a mechanism the fix may not use. Whether the phase can leave the loop
thread at all is unmeasured: `llm_broker` fairness and `card_reservation` both sit in that chain.
